# 타입 관련 작업 사항 및 순서 정리·보고

## 문서 목적

이 문서는 JBroEngine의 타입 계층을 게임엔진 성능 기준으로 정리하기 위한 설계 기준과 실행 순서를 기록한다.
구현 중 수시로 갱신하는 상세 체크리스트는 `tasks/TypeSystem.todo.md`를 사용하고, 이 문서는 장기 방향과
중요한 설계 판단을 설명하는 기준 문서로 사용한다.

## 최우선 목표

`Engine/Utillity/Types`를 단순 편의 타입 모음이 아니라 다음을 책임지는 엔진 기반 계층으로 만든다.

1. 연속적이고 예측 가능한 메모리 배치
2. 프레임 hot path에서의 할당과 분기 최소화
3. SIMD와 컴파일러 자동 벡터화에 적합한 데이터 접근
4. Windows, Android, Web의 일관된 타입·메모리 계약
5. Engine과 SDK 사이의 동일한 공개 타입 정의
6. DLL 경계에서 안전한 ABI 규칙
7. Inspector, undo/redo, 직렬화, 스크립트 codegen을 포함한 프로퍼티 연동

성능 판단 우선순위는 캐시 효율, 할당 감소, 데이터 배치, 분기 감소, SIMD, 편의 API 순이다.

## 2026-07-20 1차 구현 현황

다음 기반을 `Engine/Utillity/Types`와 SDK 미러에 추가했다.

- alignment와 memory tag를 받는 `HeapAllocator`
- relocation trait, `ArrayView`, `Hash`, `EqualTo`
- 비자명·move-only 원소 수명을 처리하는 연속 저장 `Array`
- scalar, SSE2, NEON, wasm SIMD128의 16-byte 비교 abstraction
- SIMD control metadata를 사용하는 flat hash `Table`
- `ReflectTypeDesc`, `ReflectArrayOps`, `ReflectTableOps`와 `Array` 등록 adapter

프로퍼티 연동은 기반 단계까지 구현됐다. Component 리플렉션은 컨테이너 layout을 직접 해석하지 않고
descriptor와 callback을 통해 `Array`에 접근할 수 있다. Inspector collection UI, typed undo/redo, YAML
round-trip, 중첩 Asset/Ref 수집은 아직 후속 구현 항목이며, 완료된 것으로 간주하지 않는다. Script JPROP의
owning container는 DLL ABI-safe storage가 확정되기 전까지 허용하지 않는다.

Windows x64 Release에서 20만 개 정수 원소와 임의 `uint64_t` 키를 5회 측정했다. 환경 잡음을 포함한 관측
범위이므로 절대 성능 보증이 아니라 현 구현의 최적화 기준선으로 사용한다.

| 항목 | Engine | STL | 판단 |
|---|---:|---:|---|
| Array append | 6.23~7.22 ns/element | 5.62~9.42 ns/element | 대체로 동급, 추가 반복 필요 |
| Array iterate | 0.40~0.89 ns/element | 0.32~0.49 ns/element | Engine이 느림, 코드 생성 확인 필요 |
| Table insert | 45.42~50.43 ns/element | 139.39~153.82 ns/element | Engine 약 2.8~3.3배 빠름 |
| Table hit | 45.08~61.09 ns/lookup | 32.19~40.50 ns/lookup | Engine 조회 경로 개선 필요 |
| Table miss | 50.85~56.73 ns/lookup | 39.48~54.16 ns/lookup | Engine 조회 경로 개선 필요 |

검증은 `/W4 /WX` Release smoke test에서 비자명 수명, move-only 원소, self-append, 강제 hash 충돌과 삭제,
scalar/SIMD 256×256 byte 비교, Array reflection callback을 통과했다. SDK 소비 샘플도 Release x64로 빌드됐다.
전체 Engine Debug 빌드는 신규 타입을 사용하는 PCH와 대부분의 번역 단위를 컴파일한 뒤 기존
`Engine/Editor/FileSystem/IFileWatcher.h` 누락으로 중단됐다. Android ARM64와 WebAssembly는 backend 코드를
추가했지만 실제 toolchain 빌드와 성능 검증 전이므로 완료 항목으로 표시하지 않는다.

### 성능 재설계 및 재측정

최초 단발 측정은 실행 순서와 시스템 잡음의 영향이 커서 채택 근거로 사용하지 않는다. 100만 원소 반복
중앙값, Engine/STL 교차 실행, iterator/pointer 분리 및 어셈블리 비교로 다시 검증했다. `Array`와
`std::vector`의 iterator 루프는 동일한 SSE2 누산 inner loop가 생성됐고 반복 측정에서 승패가 뒤집혀 순회는
동급으로 판정한다. reserved append도 동급 범위다.

`Array::RemoveAt`은 trivially relocatable 원소에 `memmove` fast path를 사용하고, `RemoveAll`은 검증된
`remove_if` 압축 경로를 사용한다. 65,536개 정수 기준 front ordered erase와 50% compact는 STL과 동급 이상을
확인했다. `Insert`/`EmplaceAt`, `RemoveAllSwap`도 추가했다. 다른 원소 크기와 비자명 타입 측정은 계속한다.

`Table`은 H1 probe 위치와 H2 control fragment가 일부 같은 hash bit를 쓰던 구조를 폐기하고, H2는 하위 7bit,
H1은 그 이후 bit를 사용하도록 독립 분할했다. 1K~262K 임의 `uint64_t` key에서 삽입은
`std::unordered_map`보다 약 4~8배, hit은 동급~약 2배, miss는 동급~약 6배 빨랐다. 100만 cold hit은 동급이며
miss와 삽입은 계속 우세했다. 실제 GameFramework key와 load factor별 검증 전에는 무차별 전환하지 않는다.

### 차별화 타입 전략

`Array`는 vector 복제품으로 끝내지 않고 allocator/memory tag, relocation, ordered/swap/batch removal,
reflection과 view를 결합한 GameFramework 기본 연속 컨테이너로 둔다. 순회 동급 성능은 절대 채택 조건이다.

- `SparseArray`: slot index 안정성과 빈 slot free-list 재사용이 필요한 runtime storage
- `SparseSet`: Entity/Object ID O(1) 조회와 dense component 순회를 동시에 제공하는 component storage
- `InlineArray`: 소수 원소의 heap allocation을 제거하는 collider/effect/dependency storage
- generation `HandlePool`/`SlotMap`: stale handle 검출과 객체 lifetime 안정성이 필요한 storage
- ring buffer: 이벤트와 작업 queue

범용 linked `List`는 포인터 추적과 cache miss 때문에 기본 타입으로 만들지 않는다. 실제 프로파일에서
iterator를 이미 보유한 중간 삽입·삭제가 순회보다 지배적인 명확한 사용처가 확인될 때만 검토한다.

Script JPROP은 엔진 제공 타입(`Bool`, `Int`, `UInt`, `Float`, 각도/수학/자산/Ref 타입)만 허용한다. primitive와
임의 STL 타입 별칭은 codegen allow-list에서 제거했다. 생성되는 `ScriptPropertyDesc`는 위치 기반 aggregate가
아니라 C++20 지정 초기화를 사용해 descriptor 필드 추가·재정렬이 조용한 오등록이나 빌드 회귀를 만들지 않게 했다.

### GameFramework 1차 적용

성능 게이트 뒤 첫 적용은 외부 ABI를 바꾸지 않는 Canvas 내부 runtime storage로 제한했다.

- `m_pendingDestroyObjects`, `m_pendingDestroyComponents`, `m_pendingDestroyLayers`: `Array<SafePtr<...>>`
- `m_objectByGuid`: `Table<Guid128, SafePtr<CGameObject>>`

pending destroy는 append, swap-out, 순차 flush, capacity 재사용 계약이라 `Array`와 정확히 맞는다. object GUID
인덱스는 매 프레임 `Ref::Get`이 조회하고 주소 안정성을 요구하지 않으므로, 실제 측정에서 hit/miss가 검증된
`Table` 적용 대상으로 선정했다. 다른 unordered map은 이 결과만으로 치환하지 않는다.

실제 키 타입인 `Guid128` 65,536개 hit 중앙값은 `Table` 27.46 ns, `std::unordered_map` 29.89 ns로 측정됐다.
같은 실행의 정수 key에서는 hit 40.18 ns 대 53.84 ns, miss 15.97 ns 대 77.66 ns였다.

기존 `TObjectPool`에 dense live-pointer index를 추가한 실험에서 동일 slot memory 순회 대비 50% 점유는 약 1.8배,
10% 점유는 약 7.8배 빨랐고 100% 점유에서는 약 7% 느렸다. 처음에는 고점유 회귀와 순회 순서 우려로 되돌렸지만,
호출 구조를 다시 추적한 결과 pool에는 정렬 계약이 없고 스크립트 실행 순서도 pool과 분리되어 있었다. 스크립트
메모리 풀은 할당만 담당하며, 실제 `Update`/`FixedUpdate`는 레이어·하이라키·오브젝트 컴포넌트 순서로 재구축한
`m_scriptExecutionOrder`를 순회한다. object pool에서 수집한 루트도 이 캐시를 만들기 전에 `CreationOrder`로 정렬한다.

따라서 `TObjectPool`은 dense live-pointer index를 항상 사용하는 구조로 재적용했다. `Allocate`가 live 배열 끝에
등록하고 `Free`는 swap-remove로 O(1) 제거하며, `ForEachLive` 비용은 capacity가 아니라 live count에 비례한다.
점유율에 따른 scan/dense 전환은 하지 않는다. dense 배열의 순서는 저장 구현 세부사항이며 주소 안정성만 기존과
동일하게 보장한다. 의미 있는 실행·표시·선택 순서는 pool 바깥 소비자가 명시해야 한다.

### Pool 순서와 분리해 처리할 후속 항목

다음 호출부는 현재 pool의 물리 순서를 암묵적으로 관찰한다. dense index 채택을 막는 storage 요구사항으로 두지
않고, 각 시스템의 의미에 맞는 priority/tie-break를 별도로 정의한다.

- `AudioSystem`: 첫 번째 활성 `AudioListener`를 primary로 사용 — 명시적 listener priority 필요
- `Physics2D::OverlapPoint`: 첫 번째 겹침 객체 반환 — 다중 hit 선택 기준 또는 전체 결과 API 검토
- `Physics2D::Raycast`: 동거리 hit tie-break 없음 — 안정 key 기준 필요
- `Physics2D` contact/solver: collider 수집 및 manifold 처리 순서에 따른 부동소수점 편차 — 강한 결정성이
  필요할 때 stable object key로 정렬
- `RenderScene`: 같은 layer/queue/sort key는 제출 순서를 보존 — 완전 동률의 표시 의미를 명시하거나 마지막
  tie-break key 추가

## 현재 상태 요약

현재 `Types`에는 성격이 다른 요소가 한 폴더에 섞여 있다.

- `Bool`, `Int`, `UInt`, `Float`: 스크립트와 리플렉션 편의에 가까운 값 래퍼
- `Degree`, `Radian`: 단위를 구분하는 수학 타입
- `String`: `std::string`을 공개 상속하는 owning 문자열
- `Asset`: 문자열·파일 경로 계층인 `File::Guid`를 공개 상속하는 자산 래퍼
- `Handle`, `Length`, `CWChar`: 사실상 사용되지 않는 legacy 전역 typedef
- `Types.h`, `EngineTypes.h`: 기반 타입과 수학 타입을 넓게 전파하는 umbrella

컨테이너 사용은 `std::vector` 224개 파일, `std::unordered_map` 42개 파일,
`std::map` 12개 파일에 걸쳐 있다. 따라서 전면 기계 치환은 허용하지 않고 사용 계약에 따라 단계적으로 전환한다.

현재 명시적 SIMD intrinsic, `/arch:` 계열 설정, WebAssembly `-msimd128` 설정은 확인되지 않았다.
타입 계층에서 SIMD 기반을 먼저 구축한 뒤 물리, 오디오, 렌더링 등으로 확대한다.

## 타입 계층 구조

### 값 타입

- 타입 자체가 값을 소유한다.
- 복사, 이동, 파괴의 비용과 의미가 명확해야 한다.
- 크기나 정렬이 계약이면 `static_assert`로 검증한다.
- DLL 경계 안전 여부를 별도로 명시한다.

대상: `Bool`, `Int`, `UInt`, `Float`, `Degree`, `Radian`, 향후 `AssetId`.

### owning 컨테이너

- 할당된 메모리와 요소 수명을 소유한다.
- DLL 경계를 직접 통과시키지 않는다.
- allocator와 allocation site가 동일한 모듈에 머물도록 한다.

대상: `String`, `Array`, `Table`.

### non-owning view

- 메모리를 해제하지 않는다.
- pointer와 count 이상의 소유권을 암시하지 않는다.
- hot path 함수 인자와 DLL 내부 경계 adapter에 우선 사용한다.

대상: `ArrayView`, `StringView` 또는 `std::string_view`.

### 정책·trait

- 저장 공간을 소유하지 않는다.
- hash, equality, relocation, zero construction, allocator 선택을 명시한다.

대상: `Hash`, `EqualTo`, `IsTriviallyRelocatable`, allocation traits.

## 공통 개발 규칙

- 타입 헤더는 PCH 없이 단독으로 컴파일되어야 한다.
- 헤더는 필요한 표준·엔진 헤더를 직접 include한다.
- public inheritance는 is-a 관계와 소멸·ABI 계약이 명확할 때만 사용한다.
- owning 타입과 view 사이의 변환 방향은 owning에서 view로만 암시 허용을 검토한다.
- narrowing conversion은 명시적으로 수행한다.
- 범용 인덱스와 개수에는 `Int`/`UInt`를 사용하지 않는다.
- 저수준 개수에는 `std::size_t`, 파일·프로토콜 계약에는 고정폭 정수를 사용한다.
- 반복 순서, 주소 안정성, iterator 무효화 규칙을 API 문서에 기록한다.
- Release 성능을 위해 Debug 검증을 제거할 수 있지만 객체 수명과 overflow 검사는 설계로 안전해야 한다.
- `Uninitialized`, `Zeroed`, raw relocation API는 trait로 허용된 타입에만 공개한다.
- 플랫폼 전용 intrinsic은 컨테이너 본문에 흩뜨리지 않고 내부 SIMD abstraction에 격리한다.
- scalar reference 구현을 유지해 정확성 비교와 미지원 플랫폼 fallback에 사용한다.
- 새 기능은 실제 사용처, 단위 테스트, 벤치마크가 함께 있을 때만 추가한다.

## 메모리와 allocator

컨테이너보다 먼저 또는 같은 단계에서 최소 allocator 계약을 만든다.

필수 입력:

- allocation size
- alignment
- memory tag

최초 구현은 일반 heap allocator 하나로 시작하되, 컨테이너 템플릿과 ABI가 향후 inline, arena,
frame allocator를 수용할 수 있어야 한다. allocator 자체를 가상 함수 객체로 만들어 모든 할당에 간접 호출을
추가하지 않는다. 정책 타입 또는 경량 handle 방식으로 컴파일 타임·초기화 시점에 결정한다.

`Array`는 최소 `alignof(T)`를 보장하고 16, 32, 64바이트 over-aligned 타입을 정확히 지원한다.
단순히 모든 할당을 64바이트로 정렬하면 작은 배열의 메모리 낭비가 커지므로 사용 타입이 요구하는 정렬만 적용한다.

## Array 설계 방향

`Array<T, Allocator>`는 연속 메모리 기반 owning 컨테이너다.

핵심 목표:

- `std::vector` 수준의 일반 C++ 객체 수명 정확성
- capacity를 유지하는 프레임 버퍼 재사용
- 순서가 필요 없는 삭제의 빠른 경로
- SIMD 및 자동 벡터화가 가능한 raw contiguous access
- allocator와 memory tag 연결

필수 API:

- 조회: `Size`, `Capacity`, `IsEmpty`, `Data`, `First`, `Last`
- 메모리: `Reserve`, `Resize`, `Clear`, `Reset`, `Shrink`
- 추가: `Add`, `Emplace`, `Append`, `Insert`
- 삭제: `Pop`, `RemoveAt`, `RemoveAtSwap`, `Remove`, `RemoveSwap`
- 저수준: 제한된 `AddUninitialized`, `AddZeroed`
- interop: iterator, range-for, `ArrayView`

`Array<bool>` 특수화는 만들지 않는다. bool 배열의 원소 접근이 proxy reference가 되는 문제를 엔진 타입에
재현하지 않는다. 바이트 저장은 `Array<std::uint8_t>`, 비트 밀도가 중요한 저장은 후속 `BitArray`를 사용한다.

### Array와 SIMD

`Add`나 `Remove`를 무조건 intrinsic으로 작성하지 않는다. trivial 타입의 대량 이동은 검증된
`memcpy`/`memmove`와 컴파일러 최적화를 우선한다. `Array`가 SIMD에 제공해야 하는 핵심은 정렬,
연속성, alias가 적은 view, batch 처리 가능한 데이터 크기다.

개별 `Vector2`를 16바이트 정렬해 크기를 두 배로 만드는 방식은 채택하지 않는다. 다량의 점 변환처럼
실제 병렬성이 있는 경로는 `ArrayView<Vector2>` 또는 SoA 데이터를 받는 batch API에서 SIMD화한다.

## Table 설계 방향

`Table<Key, Value, Hasher, Equal, Allocator>`은 `std::unordered_map` 대체용 flat hash table이다.
`std::map`의 정렬 의미는 대체하지 않는다.

핵심 목표:

- 노드별 할당 제거
- 키와 값의 연속 저장
- control metadata를 이용한 분기 감소
- SIMD128을 이용한 후보 슬롯 동시 탐색
- 실패 lookup과 높은 load factor에서도 안정적인 성능

Swiss Table 계열의 구조를 참고해 슬롯마다 1바이트 control metadata를 둔다. hash를 probe 위치에
사용하는 H1과 control byte 비교에 사용하는 H2로 나누고, 16개의 control byte를 한 번에 비교한다.

플랫폼 backend:

- Windows x64: SSE2
- Android ARM64: NEON
- WebAssembly: wasm SIMD128
- 기타와 검증: scalar

모든 주력 플랫폼의 기본 group width는 16바이트로 통일한다. AVX2는 타입 계층의 최초 구현에 넣지 않는다.
프로파일 결과 대규모 테이블에서 명확한 이득이 확인될 때 선택적 runtime dispatch로 추가한다.

`Table`은 flat storage이므로 rehash 때 값 주소가 이동한다. 기존 `std::unordered_map`의 노드 주소 안정성을
기대하는 사용처는 전환하면 안 된다. 주소 안정성이 필요하면 값을 `OwnerPtr`로 보관하거나 별도 node/stable
컨테이너를 검토한다.

## SIMD 내부 계층

SIMD 추상화는 일반 벡터 수학 라이브러리로 크게 시작하지 않는다. 최초 범위는 `Table`의 control-byte
탐색에 필요한 128비트 정수 연산으로 제한한다.

초기 기능:

- 16개의 8비트 lane load
- 8비트 값 broadcast
- lane equality compare
- empty/deleted 상태 compare
- match bit mask 생성
- first-set-bit 및 mask iteration 보조 함수

이 범위는 SSE2, NEON, wasm SIMD128에서 직접 대응 가능하고 scalar reference 구현도 단순하다.
타입 계층 밖의 물리·오디오 SIMD는 이 기반을 재사용할 수 있는지 검토하되, 억지로 같은 abstraction에
끼워 넣지 않는다.

## 기존 타입 정리 방향

### `Bool`, `Int`, `UInt`, `Float`

현재 암시 생성과 기본형 변환을 모두 허용하므로 엄격한 strong type은 아니다. 스크립트·리플렉션 값 타입으로
역할을 한정하고 컨테이너 index나 byte count에는 사용하지 않는다. 암시 변환 제거는 SDK 호환성에 영향을 주므로
컨테이너 도입과 분리해 처리한다.

### `Degree`, `Radian`

유지한다. 단위 구분은 가치가 있다. 다만 상호 include 구조를 분리하고 exact equality와 nearly-equal 사용 기준을
정리한다. 개별 각도 타입에 무리한 SIMD를 넣지 않고 angle array의 batch 처리에서 SIMD를 사용한다.

### `String`

최초 컨테이너 단계에서는 기존 ABI를 유지한다. `Split` 결과를 `Array<String>`으로 바꾸고 새 hash 정책에 연결한다.
public `std::string` 상속 제거와 custom allocator 연결은 독립 마이그레이션으로 진행한다.

### `Asset`과 GUID

런타임 lookup key는 경로 문자열 기반 `File::Guid`보다 고정 크기 `Guid128`이 적합하다. 장기적으로
`AssetId`를 고정 크기 값 타입으로 만들고 YAML 직렬화 경계에서만 문자열로 변환한다. 이는 `Table`의 hash와
equality 비용을 줄이고 DLL 경계 표현도 명확하게 만든다.

### legacy typedef와 umbrella

`Handle`, `Length`, `CWChar`는 재검증 후 제거한다. `Types.h`에 수학 헤더를 섞지 않고, 각 공개 헤더는 필요한
타입을 직접 include한다. `EngineTypes.h`는 스크립트 공개 편의가 필요한 제한된 위치에서만 사용한다.

## 프로퍼티 시스템 연동 분석

### 현재 파이프라인과 제약

현재 프로퍼티는 Component `AddProperty` 또는 Script `JPROP`/`REFLECT_FIELD`로 등록되고,
`EReflectPropertyType`과 `ReflectPropertyInfo`를 거쳐 Inspector, YAML serializer, undo/redo command로 전달된다.
Script JPROP은 프로젝트 생성기가 C++ 타입 문자열을 파싱해 generated registry를 만든다.

현재 구조는 scalar와 고정 layout 값 타입을 전제로 한다. 메타데이터에는 단일 `Type`, `Offset`, `Size`,
`ElementCount`만 있어 Array element 또는 Table key/value 타입과 생성·파괴·복사 연산을 표현할 수 없다.
`ElementCount`도 현재 일반 collection이 아니라 고정 char buffer 문자열을 구분하는 용도로만 실질 사용된다.

Inspector undo/redo는 `String`만 별도 처리하고 다른 타입은 `property.Size`만큼 raw `memcpy`한다. 따라서
heap pointer, size, capacity를 가진 `Array`나 `Table`을 현재 방식으로 등록하면 얕은 복사, 이중 해제,
allocator 불일치 또는 손상된 undo 상태가 발생한다.

### 재귀 타입 descriptor

기존 scalar enum 호환성을 유지하면서 element/key/value 타입을 재귀적으로 기술하는 descriptor를 추가한다.

```cpp
enum class EReflectTypeKind
{
    Scalar,
    Enum,
    Ref,
    Struct,
    Array,
    Table
};

struct ReflectTypeDesc
{
    EReflectTypeKind Kind;
    EReflectPropertyType LegacyType;
    std::size_t Size;
    std::size_t Alignment;
    const ReflectTypeDesc* Element;
    const ReflectTypeDesc* Key;
    const ReflectTypeDesc* Value;
    const ReflectArrayOps* ArrayOps;
    const ReflectTableOps* TableOps;
};
```

정확한 이름과 배치는 구현 전에 확정한다. 핵심은 Inspector와 serializer가 container layout을 직접 cast하지
않고 등록된 타입소거 callback으로만 접근하는 것이다.

Array ops에는 size/capacity 조회, 원소 주소, resize, 기본 삽입, 삭제, 이동, clear가 필요하다.
Table ops에는 count, key/value 주소, 중복 검사와 삽입, 삭제, clear가 필요하다. callback은 컨테이너를
소유한 모듈에서 실행되어야 한다.

### Array 프로퍼티

`Array<T>`를 첫 collection 프로퍼티로 지원한다.

- 접기/펼치기와 size 표시
- 원소 추가·삭제·복제·순서 이동
- 원소별 재귀 property editor
- YAML sequence 저장·복원
- 변경 단위 undo/redo
- 원소 내부 Asset/Ref 재귀 수집
- 큰 배열의 visible range만 그리는 virtualized UI

undo는 raw memory snapshot이 아니라 typed deep-copy, property serialization snapshot 또는 collection command를
사용한다. 최초 구현은 정확성이 단순한 typed snapshot으로 시작하고, 대형 collection에서 비용이 확인되면
추가·삭제·이동·원소 변경 command로 세분화한다.

### Table 프로퍼티

`Table` 프로퍼티는 Array 이후에 지원한다. 정수, enum, String, 고정 크기 GUID/AssetId처럼 결정적으로
표시·직렬화 가능한 key만 우선 허용한다. 포인터, float, 런타임 handle은 reflected key 기본 대상에서 제외한다.

hash iteration 순서는 저장 순서로 사용하지 않는다. YAML 저장 전에 key를 정렬하거나 pair sequence를 안정
정렬하여 동일 데이터가 동일 파일을 만들게 한다. 문자열 key가 아닌 일반형은 다음 표현을 우선 검토한다.

```yaml
Entries:
  - Key: Player
    Value: 10
  - Key: Enemy
    Value: 20
```

### Component와 Script의 차이

Engine Component는 호스트 모듈에서 생성·파괴되므로 owning `Array/Table` 프로퍼티를 직접 가질 수 있다.

게임 Script는 DLL 경계를 넘고 현재 프로젝트 규칙상 필드가 POD여야 한다. `JPROP() Array<T>`나
`JPROP() Table<K, V>`를 단순 허용하면 안 된다. 기본 권장안은 Script 필드에 POD handle만 두고 실제
collection storage를 호스트 또는 별도 property storage가 소유하는 방식이다.

대안으로 모든 생성·접근·복사·파괴를 게임 DLL callback 안에서 수행할 수 있지만 DLL unload 전에 storage를
완전히 파괴하는 강한 lifetime protocol이 필요하다. 라이브 리로드 안정성을 고려하면 handle 기반 외부 storage를
우선 설계한다. 이 설계가 확정되기 전까지 Script JPROP owning container 등록은 codegen 단계에서 거부한다.

### JPROP codegen

현재 프로젝트 생성기는 정규식과 단순 문자열 비교로 타입을 enum에 매핑한다. `Array<T>`는 angle bracket을,
`Table<K, V>`는 중첩 template과 comma를 포함하므로 기존 조건문만 확장하면 쉽게 깨진다.

필요한 작업:

- template nesting depth를 추적하는 경량 type parser
- top-level comma 분리
- namespace와 공백 정규화
- element/key/value 재귀 매핑
- 미지원 타입의 생성 시점 오류
- generated registry에 type descriptor와 ops callback 생성

### 직렬화, 에셋 참조와 에디터 UI

serializer는 descriptor를 재귀 방문하여 중첩 Array, struct 원소, Asset/Ref 원소와 Table value 내부 참조까지
처리해야 한다. 패키징 누락을 막기 위해 collection 내부 참조도 referenced-assets 수집에 포함한다.

raw byte editor command는 trivial property에만 허용하고 `String`, `Array`, `Table`은 typed snapshot command를
사용한다. 추가·삭제·이동은 각각 undo 가능한 command가 되어야 하며 Table key 변경은 중복 검사를 통과한 뒤
commit한다. 모든 추가·삭제·오류 UI 문자열은 한국어·영어 localization key를 함께 등록한다.

## 성능 검증 기준

각 최적화는 scalar, STL baseline, SIMD backend를 같은 workload로 비교한다.

필수 측정:

- ns/op과 cycles/element
- 성공 lookup과 실패 lookup
- 작은/중간/큰 데이터셋
- 낮은/높은 load factor
- L1/L2/LLC miss
- branch miss
- allocation 횟수와 총 bytes
- peak/resident memory
- 코드 크기

벤치마크 변동폭보다 작은 차이는 개선으로 인정하지 않는다. 하나의 데스크톱 CPU에서만 빠른 구현도 완료로
간주하지 않는다. Windows x64, Android ARM64, WebAssembly에서 정확성과 대표 성능을 확인한다.

## ABI와 SDK 원칙

`Array`, `Table`, `String`은 owning 타입이며 호스트와 게임 DLL 사이의 안전한 데이터 계약이 아니다.
경계에서는 다음만 사용한다.

- POD 구조체
- pointer와 count
- caller-owned output buffer
- 고정 크기 ID
- opaque handle
- 동일 모듈 안에서 생성과 파괴가 끝나는 callback

Engine과 SDK의 타입 헤더는 같은 내용을 수동으로 두 벌 관리하지 않는다. 배포 시 복제하더라도 Engine 헤더를
단일 원본으로 취급하고 자동 복제 및 hash 검사를 둔다.

## 현재 결론

첫 SIMD 채용 지점은 `Table`의 16바이트 control metadata 탐색으로 한다. `Array`는 정렬과 연속성,
relocation, view를 제공해 SIMD의 기반이 된다. 기존 숫자·각도 타입에 intrinsic을 개별 삽입하지 않고 다량의
데이터를 처리하는 batch 연산에서 SIMD를 사용한다.

타입 계층이 안정된 뒤 물리, 오디오, 렌더링으로 SIMD를 확대한다. 이 순서는 타입 기반을 먼저 완성하면서도
게임엔진의 실제 성능 목표를 잃지 않는 진행 방식이다.

프로퍼티 연동은 타입 작업의 부가 기능이 아니라 완료 조건에 포함한다. Component의 Array/Table은 typed
reflection으로 지원하고, Script JPROP은 DLL POD 규칙을 만족하는 storage가 확정되기 전까지 owning
container를 노출하지 않는다.

## 2026-07-20 Engine/Application 적용 현황

이번 단계에서 타입 메타데이터의 실제 소비 경로를 연결했다.

- 새 스크립트 UI: `Asset` scalar, 유효한 asset/component Ref 대상, grouped component header,
  Serialize/Range 옵션을 코드 생성 규칙과 일치시켰다.
- 스크립트 리플렉션: generator가 scalar descriptor를 만들고 registry가 이를 보존한다.
- 엔진 컴포넌트: `Array` type-erased ops에 재정렬을 추가하고 Inspector의 추가/삭제/이동/비우기,
  owning-memory 안전 YAML snapshot undo/redo, YAML 저장/복원, asset dependency 수집을 연결했다.
- 대표 적용: `AudioPlayer.EffectGuids`의 수동 vector UI/직렬화를 제거하고
  `Array<AssetGuid>` 리플렉션 프로퍼티로 전환했다. 기존 단일 `EffectGuid` 읽기 호환은 유지한다.

남은 작업은 다음과 같이 분리한다.

- 게임 스크립트 DLL에는 owning `Array/Table`을 아직 노출하지 않는다. 모듈 간 할당/해제 및
  unload/reload 수명을 보장하는 ABI-safe storage가 먼저 필요하다.
- `Table`은 key/value type-erased ops가 부족해 Inspector/YAML/undo가 아직 없다.
