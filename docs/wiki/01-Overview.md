# 1. 엔진 개요

## 무엇인가

JBroEngine 은 Windows 에서 D3D12 로 그리는 게임 엔진이다. 지금은 2D 제작에 집중하지만,
코어·렌더러·RHI 는 3D 를 막지 않게 짜여 있고 3D 빌트인 컴포넌트도 이미 들어 있다.

만드는 사람이 쓰려는 흐름은 이렇다.

1. 엔진을 한 번 설치한다. 2D 판, 3D 판이 따로 있지 않다.
2. 새 프로젝트를 만들 때 2D 인지 3D 인지 고른다. 그 선택은 **스크립트 프로젝트의 include 경로**와 **게임 익스포트 링크**에만 반영된다.
3. 에디터에서 씬(`.jcanvas`)을 편집하고, 게임 로직은 스크립트 DLL 로 빌드해 실행 중에 갈아 끼운다.

이 엔진은 기존 엔진(`JBroEngine_old`)을 다시 세운 것이다. 기존 엔진의 오브젝트-컴포넌트 모델과 에디터 경험은 그대로 이어받되,
모듈 경계, 참조 모델, 리플렉션, DLL ABI 는 처음부터 새로 정했다. 어떤 부분을 왜 다르게 했는지는
[설계 결정의 근거](12-Design-Decisions.md)에 모아 두었다.

## 한 장 그림

```
┌─ 호스트 실행 파일 ──────────────────────────────────────────────┐
│  JBroGameHost (게임 실행)      JBroEditorHost (에디터)            │
│      └── EngineInstance : 프로세스 자원 전부를 소유하고 조립한다   │
│             ├─ IPlatform(창·입력)   ├─ IRHIDevice(D3D12)          │
│             ├─ Renderer(패킷 수집·기록)   ├─ AssetSystem [스텁]     │
│             └─ IFramework : 프로젝트가 고른 차원의 Framework2D/3D  │
│                    └─ Canvas : 오브젝트 풀·컴포넌트 풀·레이어·시스템 │
│                          └─ GameObject ── ComponentBase 들          │
└─────────────────────────────────────────────────────────────────┘
        ▲ ScriptModuleLoadContext (POD)        ▼ ScriptRegistry 에 타입 등록
┌─ 게임 스크립트 DLL ────────────────────────────────────────────┐
│  <JBro/ScriptAPI.h> 하나만 include 한다                          │
│  GameScript2D 를 상속한 사용자 스크립트, GameObjectHandle, Ref<T>  │
│  엔진 실체(Canvas·GameObject·Renderer·RHI)는 선언조차 보이지 않는다 │
└─────────────────────────────────────────────────────────────────┘
```

호스트는 스크립트 DLL 에 **필요한 부분집합만** 넘긴다. DLL 은 시스템 인터페이스 포인터와 서비스 값을 받아 자기 정적 링크 사본에
바인딩하고, 그 뒤로는 함수 테이블을 거치지 않고 바로 부른다. 자세한 것은 [스크립트 경계](05-Script-Boundary.md).

## 지금 어디까지 왔나

2026-09-15 기준이다. 커밋 수는 294개다.

| 영역 | 상태 |
|---|---|
| 오브젝트-컴포넌트 모델, `Canvas`, 풀, 레이어 | 서 있다. 할당 0회·조회 0회 성능 계약을 테스트가 단언한다 |
| 참조 모델(`GameObjectHandle`, `Ref<T>`, `InstanceRegistry`) | 서 있다. 핫 리로드 뒤 슬롯 캐시 무효화는 아직 열려 있다 |
| 스크립트 DLL 로드·언로드·재로드 | 서 있다. 실제 V1→V2 DLL 교체까지 실측했다 |
| 리플렉션(`JBRO_FIELD`, `PropertyInfo`, 코덱, 컨테이너 조작) | 서 있다. 2D·3D 빌트인 컴포넌트 열 개가 등록돼 있다 |
| 직렬화(`.jcanvas` 읽기·쓰기, `.jproject` 읽기) | 서 있다. 저장→로드→저장이 같은 글자를 낸다 |
| 렌더러(스프라이트 패킷, 정렬, 텍스처 바인딩), D3D12 RHI | 서 있다. 검증 레이어가 조용한지까지 테스트가 본다 |
| 에디터(패널 넷, 인스펙터, 계층, 되돌리기, 여럿 고르기) | 서 있다. 뮤테이션 150개 남짓으로 쟀다 |
| 에셋 로드 | **[스텁]**. `AssetId` 는 저장되지만 `AssetHandle` 을 채우는 패스가 없다 |
| 물리 | 중력·감쇠·속도 적분과 레이캐스트·박스 오버랩 쿼리가 있다. 충돌 해결은 없고 `OnCollisionEnter/Exit` 는 아직 아무도 부르지 않는다 |
| 3D 렌더 시스템 | 없다. `Framework3D::Render()` 는 `NothingToSubmit` 을 돌려준다 |
| JBroScript 언어, `jbroc` | **[계획]**. 문법과 컴파일러 규칙 문서만 있다 |
| 스크립트 편집기(Code-OSS 포크) | **[계획]**. 문법 강조 확장만 별도 리포에 있다 |
| Web 빌드 | 스텁. 지원 완료로 치지 않는다 |

## 자주 나오는 용어

| 용어 | 뜻 |
|---|---|
| **Canvas** | 최상위 실행 단위. 오브젝트 풀·컴포넌트 풀·레이어·시스템 스케줄러를 직접 소유한다. `World`·`Scene` 같은 중간 계층은 없다 |
| **GameObject** | 실체 객체. 부모·자식·레이어·태그·활성 상태가 멤버다. Transform 은 멤버가 아니라 컴포넌트다 |
| **ComponentBase** | 모든 컴포넌트의 다형성 베이스. 타입별 풀에 살고, 논리 소유는 오브젝트가 한다 |
| **GameScriptBase / GameScript2D** | 스크립트의 베이스. 컴포넌트의 일종이다. `OnCreate`·`OnStart`·`OnUpdate`·`OnFixedUpdate`·`OnDestroy` 훅을 가진다 |
| **System** | 엔진 계층의 로우레벨 객체. 매 프레임 컴포넌트 풀을 순회하며 갱신한다. 스크립트는 만질 수 없다 |
| **Service** | 스크립트에 공개하는 얇은 API. 값으로 `ServiceContext` 에 담긴다. 예: `Service::Physics2DService` |
| **Tier S / Tier E** | 스크립트가 보는 모듈 층 / 엔진만 보는 모듈 층. include 경로로 강제한다 |
| **InstanceId** | 64비트 영속 식별자. 저장 파일에 적히는 값이다 |
| **InstanceHandle** | `{Slot, Gen}` 8바이트. 이번 실행에서의 위치다. 저장하지 않는다 |
| **GameObjectHandle** | 스크립트가 오브젝트를 들고 있을 때 쓰는 16바이트 값. 무효면 로그만 남기고 아무 일도 하지 않는다 |
| **Ref\<T\>** | 스크립트가 컴포넌트·스크립트를 들고 있을 때 쓰는 24바이트 값. 저장·로드·핫 리로드를 넘는다 |
| **SafePtr / OwnerPtr** | 엔진 내부의 비소유 참조 / 고유 소유. 메인 스레드 전용이다 |
| **프렐류드** | 스크립트가 include 하는 단 하나의 헤더 `<JBro/ScriptAPI.h>`. `using namespace JBro;` 를 한다 |
| **PropertyInfo / TypeDescriptor** | 필드 하나의 명세 / 타입 하나의 명세. 인스펙터와 직렬화가 읽는다 |
| **Decisions (D-번호)** | `tasks/todo.md` 에 적힌 확정 결정. 문서 초안보다 우선한다 |

## 파일 형식

| 확장자 | 무엇 | 형식 |
|---|---|---|
| `.jproject` | 프로젝트 설정 | YAML. 키 이름은 기존 엔진과 같다. 두 번째 형식을 만들지 않는다 |
| `.jcanvas` | 씬(캔버스) | YAML 부분집합. 리플렉션 표를 따라 쓰고 읽는다 |
| `.jscript` | JBroScript 소스 **[계획]** | 텍스트. `jbroc` 이 C++ 로 바꾼다 |
| `.hlsl` → `.generated.h` | 셰이더 | HLSL 원본과 컴파일된 DXIL 헤더를 함께 커밋한다. 빌드는 HLSL 을 컴파일하지 않는다 |

기존 엔진의 확장자 체계를 그대로 따른다. `.j`+이름은 사용자·에셋 파일, `.jb`+이름은 빌드 산출물이다.
