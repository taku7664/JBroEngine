# 12. 설계 결정의 근거

방향을 정한 결정들을 **주제별로** 모아 왜 그렇게 했는지 적었다. 원문은 `tasks/todo.md` 의 Decisions 절이고 번호가 그 문서의 D-번호다.
결정은 뒤 번호가 앞 번호를 고칠 수 있다(`Updates`). 여기서는 최종 상태만 적고, 바뀐 이력은 원문에서 본다.

판단 순서는 언제나 **정확성 → 단순성 → 영향 범위 최소화 → 검증 가능성 → 유지보수성 → 작업 속도**다.
그리고 "나중에 바꾸는 비용이 큰 계약은 지금 확정한다" 가 2026-09-12 구조 검토의 기준이었다.

## 모델

**ECS 를 쓰지 않는다. 오브젝트-컴포넌트 모델이다.** (D-1)
기존 엔진이 이미 이 구조이고, 리플렉션과 직렬화가 컴포넌트의 다형성에 기댄다. `Entity` 정수 ID 도, 다중 타입 `Query<A,B>` 도 없다.
시스템은 `ForEach<T>` 로 타입별 풀을 순회하고, 순회가 실체 참조를 주므로 `Ref<T>` 해석 비용이 없다.

**`World` 도 `Scene` 도 없다. 수명 계층은 `Canvas` → `GameObject` 하나다.** (D-2)
금지 대상은 이름이 아니라 중복 수명 계층 자체다.

**Transform 은 컴포넌트다. 부모·자식·레이어는 `GameObject` 멤버다.** (D-3)
기존 엔진은 2D 전용이라 Transform 을 멤버로 뒀지만 여기는 2D 와 3D 를 함께 지원한다. `GameObject` 가 차원을 모르려면 Transform 이 컴포넌트여야 한다.

**월드 변환 캐시는 `Transform2D` 안에 있다.** (D-47)
별도 `WorldTransform2D` 컴포넌트를 시스템이 자동 부착하는 안은 기각했다. 사용자가 붙이지 않은 컴포넌트가 인스펙터와 프리팹 diff 에 나타난다.

**`ComponentBase` 의 가상 함수 여섯 개를 고정한다.** (D-48)
스크립트 DLL 이 파생하는 타입의 vtable 은 ABI 다. 추가는 D-28 재빌드 규약 위에서만 한다.

**스크립트 실행 순서와 변이 경계는 구 엔진 계약을 그대로 가져온다.** (D-45)
레이어 순서 → 계층(부모 먼저) → 부착 순서. 순회 중 생성은 즉시, 목록 반영은 다음 프레임. 순회 중 파괴는 지연 큐. 구 엔진이 이미 겪고 정한 것을 다시 겪지 않는다.

**`Layer` 는 식별자와 순서 캐시를 분리하고, 2D 합성 상태는 `Layer2D` 가 갖는다.** (D-40, D-41, D-46)
공통 `Canvas` 에 수명 콜백을 달지 않기 위해 `Layer2D` 는 지연 생성한다. 등록 누락으로 재발하는 종류의 버그를 아예 없앤다.

## 참조

**스크립트에 노출하는 참조는 `GameObjectHandle`(16B)과 `Ref<T>`(24B) 둘뿐이다. 크기는 영구 고정이다.** (D-5, D-44)
타입마다 핸들을 코드 생성으로 만들면 생성 전까지 사용자 코드가 컴파일되지 않아 스크립트를 막 작성한 시점에 편집기가 깨진다(D-6).

**`GameObjectHandle` 의 무효 접근은 로그 후 무시한다. `operator->` 는 없다.** (D-8)
크래시도 예외도 절반 실행도 없어야 사용자가 `if` 없이 안전하다. `Ref<T>::operator->` 는 이 보장을 하지 않는다. 선택은 사용자가 한다.

**`Ref<T>` 의 접근자는 하나다.** (D-7)
스코프 객체로 강제하려던 안은 C++17 보장된 복사 생략 때문에 강제가 되지 않아 버렸다.

**엔진 내부는 `SafePtr` 그대로다. 핸들은 스크립트 표면에만.** (D-4)
실제로 댕글링이 나는 곳은 스크립트가 다른 오브젝트를 오래 들고 있는 자리다. 거기만 덮는다.

**영속 식별자는 64비트 `InstanceId` 하나다.** (D-9, D-59)
타임스탬프 42비트 + 세션 난수 10비트 + 시퀀스 12비트. 시간순 정렬이라 생성 순서 필드를 흡수하고, 해시맵 지역성이 순수 난수보다 좋다. 세션 비트는 한 실행 안의 비충돌만 보장한다.

**`InstanceRegistry` 는 프로세스 전역이고 캔버스를 모른다. DLL 에 1회 바인딩한다.** (D-26, D-44)
캔버스가 두 벌(에디터 편집본 + Play 사본)이어도 해석이 모호하지 않다. "어느 캔버스에 생성하는가" 는 해석이 아니라 서비스의 문제다.

**`GetComponent<T>` 는 `Ref<T>` 를 돌려주고, 첫 번째만 준다. 조회는 선형 순회다.** (D-30, D-31)
컴포넌트 5개 기준 캐시-핫 배열 순회가 해시 조회보다 빠르고, 매 프레임 순회는 시스템이 `ForEach` 로 하므로 `GetComponent` 는 초기 캐싱 용도다.

## 경계

**모듈을 Tier S 와 Tier E 로 물리 분리한다.** (D-42)
include 경로가 강제하므로 이름 규칙이 필요 없다. 기각한 안은 프렐류드 음성 테스트만 늘리기(직접 include 를 못 막는다)와 한 모듈에 include 루트 둘(빌드 단위 원칙과 충돌).

**DLL 경계는 게임 스크립트 하나뿐이다.** (D-14)
초안은 전 모듈 DLL 화의 근거로 프로세스 간 코드 페이지 공유를 들었지만, Windows 는 동일 EXE 이미지도 같은 방식으로 공유한다. DLL 의 실질 가치는 핫 리로드와 런타임 백엔드 교체뿐이다.

**DLL 은 C 심볼 하나(`JBroScriptModule_GetApi`)를 내보내고, 차원별 Context 는 확장 블록으로 넘긴다.** (D-37)
C++ 가상 모듈 객체는 컴파일러·CRT·할당자 ABI 를 경계에 고정한다. Context 별 심볼은 Framework 가 늘 때마다 로더를 고쳐야 한다.

**`SystemContext` ABI 는 재빌드 강제 + 버전 스탬프다.** (D-28)
게임 DLL 은 사용자 프로젝트마다 호스트와 함께 빌드된다. 매 프레임 함수 테이블은 오버헤드라 채택하지 않았다.

**서비스는 값으로, 시스템은 인터페이스 포인터로.** (D-34)
서비스 포인터는 사용자 코드에 null 검사와 수명 혼동을 퍼뜨린다. 구체 시스템 포인터는 프렐류드를 오염시킨다.

**차원별 시스템·서비스는 공통 Context 에 넣지 않는다.** (D-36, D-43)
넣으면 3D 바이너리의 공통 Context 에 2D 슬롯이 남고 공통 계층이 Framework2D 를 참조하게 된다.

**2D/3D 배타성은 사용자 스크립트 프로젝트와 게임 익스포트에만.** (D-15)
제품 플로우가 "엔진 1회 설치 → 새 프로젝트 → 2D/3D 선택" 이므로 엔진을 두 판으로 나누지 않는다.

**수학 타입은 차원별 모듈에, `Color` 같은 차원 독립 값 타입만 Core 에.** (D-38, D-57)
벡터는 차원이 곧 의미다. 2D 프로젝트가 3D 수학을 링크하지 않는다.

**`EngineContext` 타입은 없다. `EngineInstance` 자체가 그 자리다.** (D-53)
죽은 계약을 지우고 골격은 "미완" 으로 명시했다.

**Windows 스크립트 DLL 은 같은 디렉터리의 임시 복사본으로 로드한다.** (D-39)
파일 잠금 때문에 빌드 출력을 교체할 수 없는 문제를 풀되, 의존 DLL 탐색 위치를 바꾸지 않기 위해 같은 디렉터리다.

## 렌더링

**`Submit*` 은 즉시 드로우가 아니라 패킷 수집이다.** (D-29 → D-32)
`JBroGraphics` 가 `RenderWorld2D` 를 인자로 받으면 Framework2D 로의 역방향 의존이 생긴다. 그래서 Framework 가 POD 패킷을 넘기고 렌더러는 프레임 끝에 기록한다.

**스프라이트 변환은 아핀 6 + 깊이 1 이다.** (D-54)
4x4 로 넘길 때 사라지던 것은 항상 같던 두 행뿐이다. 인스턴스가 80B → 44B.

**정렬은 Framework 가 제출 전에 끝낸다. 렌더러는 받은 순서대로 그린다.** (D-53, D-46)
`(키, 인덱스)` 만 정렬하고 아이템은 제자리에 둔다.

**RHI 는 텍스처·샘플러를 슬롯에 직접 묶는다.** (D-61)
바인드 그룹은 지금 필요보다 크고, 바인들리스는 초기 설정이 크다. 나중에 옮겨도 바뀌는 것은 백엔드와 셰이더이고 호출부는 한 줄이다.

**게임 뷰는 렌더 타깃 하나 차이다.** (D-63)
경로가 갈리면 에디터에서 보는 것과 실행했을 때 보는 것이 달라지고 그 어긋남은 한참 뒤에야 드러난다.

**디바이스 로스트는 치명 오류로 종료한다. 대신 디바이스 포인터를 밖으로 내보내지 않는다.** (D-16)

**`GraphicsSystem` 은 폐기하고 `Renderer` 가 디바이스 부착을 흡수한다.** (D-17)

## 리플렉션과 언어

**게임 스크립트 언어를 자작하고 C++ 로 트랜스파일한다.** (D-56)
기존 엔진의 `JPROP` 는 정규식 파서 위에 서 있어 `Array<Ref<T>>` 를 놓쳤다. VM 을 만들면 GC·인터프리터·디버거를 다 만들어야 하지만 트랜스파일은 `#line` 하나로 VS 디버거가 원본을 보여 준다(실측).
언어는 대체가 아니라 추가 프론트엔드다. 막혀도 엔진은 멀쩡하다.

**리플렉션은 형식 하나(`PropertyInfo`), 생산자 둘.** (D-56)
타입의 사실은 `TypeDescriptor` 에, 필드의 사실은 `PropertyInfo` 에. 접근은 오프셋이 아니라 접근자 하나. 닫힌 타입 enum 을 두지 않는다.

**보관함은 둘이다.** 빌트인은 엔진 수명, 스크립트는 DLL 수명이라 한 그릇에 섞지 않는다.

**기본값과 같은 프로퍼티도 저장한다.** 나중에 기본값을 바꾸면 기존 씬이 조용히 같이 바뀌는 것이 가장 찾기 어려운 버그다.

**`String` 은 `std::string` 래퍼로 영구 확정하고, 경계와 핫 데이터에서는 금지한다.** (D-51)
이름·태그는 `NameId` 정수로. 다시 구현하지 않는다.

**컨테이너 할당기 정책은 상태를 가질 수 있고, 프레임 임시 배열은 선형 할당기를 쓴다.** (D-52)
되감는 주체는 프레임을 여는 `EngineInstance::Tick` 이다. 프레임을 여는 쪽이 프레임 메모리를 소유한다.

**에셋은 값 타입 모듈과 시스템 모듈로 나누고 `AssetManager` 는 `AssetSystem` 으로.** (D-50)

## 에디터

**ImGui, 소스째로 `ThirdParty/`, 백엔드는 RHI 위에 직접.** (D-60)
인스펙터는 매 프레임 프로퍼티 표에서 다시 그려지는 것이고 이미모드가 그 모양이다. `imgui_impl_dx12` 를 쓰면 RHI 가 감춘 핸들을 도로 꺼내야 한다.

**입력은 플랫폼이 이벤트로 모아 준다.** (D-62)
폴링식은 한 프레임 안의 키 순서와 글자 입력이 사라진다. 에디터 텍스트 필드가 그것을 필요로 한다. 키는 물리 키, 글자는 따로.

**에디터 실행 파일을 따로 둔다.** (D-65)
그때까지의 확인은 전부 숨긴 창의 백버퍼를 되읽는 것이었고, "칠해졌다" 는 알아도 "제대로 보인다" 는 몰랐다.

**패널 훅은 다섯이다.** (D-70)
기존 스물한 개 중 실제 패널이 override 하는 것을 세어 보니 다섯뿐이었다. 나중에 넣는 것이 지우는 것보다 쉽다.

**편집은 커맨드로만. 드래그 하나가 되돌리기 하나.** (D-71)
**커맨드는 포인터가 아니라 에디터 번호로 가리킨다.** (D-72) 삭제를 되돌리면 주소가 달라진다.
**되살릴 수 없는 것은 하지 않는다.** (D-76) 성공했다고 말하면서 조용히 잃는 것이 가장 나쁘다.
**여럿을 한 번에 바꾸면 전부 되거나 하나도 안 된다.** (D-83) **여럿 고른 대상에는 결과 값이 아니라 연산을 다시 적용한다.** (D-83, D-86)
**한 손짓이 여럿을 바꾸면 커맨드도 하나다.** (D-84) **되돌리기는 자리까지 되살린다.** (D-85)

**생김새는 기존 엔진 것을 그대로.** (D-73) 눈으로 맞춰 가며 깎은 값이다. 바꿀 이유가 생기면 그 이유를 적고 바꾼다.

**한국어 문구는 번역체로 쓰지 않고, 컴포넌트 이름은 번역하지 않는다.** (D-91)

## 검증

**그래픽 테스트는 검증 레이어가 조용한지까지 본다.** (D-64)
가드를 지워도 그림이 같아 뮤테이션이 죽지 않는 일이 두 번 나왔다.

**검증 레이어가 조용해도 GPU 는 죽을 수 있다.** (D-75)
프레임 밖에서 명령 할당자를 되감기 전에 그 프레임을 기다린다. API 호출은 흠이 없어 레이어가 아무 말도 하지 않고, 프레임이 밀려 있을 때만 죽는다.

**테스트 프로세스의 단언은 대화상자를 띄우면 안 된다.** (D-69)
멈춘 것과 실패한 것을 구분할 수 없게 된다. 이쪽이 터지는 것보다 나쁘다.

**뮤테이션이 살아남으면 "죽일 수 없는 것" 과 "안 잰 것" 을 가른다.** (D-77)
동치라고 판단했으면 근거를 적는다. 테스트를 지어내 숫자를 맞추지 않는다.

**좁은 문자열 리터럴은 UTF-8 이다.** (D-74)
없으면 MSVC 가 코드 페이지 949 로 인코딩하고 한글이 화면에서 깨지는데 컴파일러는 경고만 하고 지나간다.

**작업마다 관련 문서를 갱신한다.** (D-90)
대화에만 나오고 문서에 없는 결정·실측은 없는 것으로 본다. 다음 작업은 문서만 보고 시작할 수 있어야 한다.
