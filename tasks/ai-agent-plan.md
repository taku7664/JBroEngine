# 내장 AI 에이전트

사용자 승인: 2026-10-16. Codex app-server를 첫 연결로 사용하고, 요청한 작업은 직접 수행하며 사용법·위치 질문에는 현재 상태에 맞는 가이드를 생성한다. 드래그 첨부 UI는 후속 사용자 요청으로 추가했고 이미지 입력은 후속이다. 결정 D-338.

## 구현 계약

- `Agent::IProvider`와 `CodexProvider`는 엔진 도구 구현에서 분리한다. `IProcessChannel`의 비동기 stdin/stdout을 사용한다. 줄 단위 JSON-RPC는 AI 통신 내부 경계에서만 쓰고 공개 인터페이스에 JSON 라이브러리 타입을 노출하지 않는다.
- 초기화 → 공식 config/read로 현재 프로젝트 설정 확인 → 엔진 배포 스킬 루트 등록 → 계정 조회/로그인 → 프로젝트별 대화 시작/복원 → MCP 전체 목록 확인 순서다. 실행 파일은 탐색하거나 사용자가 지정하며 자동 설치하지 않는다. 인증은 Codex에 맡기고 인증 파일을 읽지 않는다. API 키는 프로젝트/대화/엔진 설정에 저장하지 않는다.
- Codex의 기본 셸·일반 실행·자식 에이전트·앱·원격 플러그인·내부/외부 브라우저·컴퓨터 제어·코드 모드·훅 기능을 해당 자식 프로세스에서 끄고 read-only sandbox와 엔진 전용 동적 도구를 사용한다. 공식 설정 조회에 제한 기능이 여전히 활성 상태이면 대화 생성 전에 거절한다. 상속된 MCP/플러그인 항목을 각각 enabled=false로 덮어쓰며, 모든 MCP 목록 페이지에서 도구·리소스·활성 연결이 없음을 확인하기 전에는 사용자 턴을 허용하지 않는다. 빈 맵은 설정을 제거하지 못한다. 사용자 전역 설정 파일은 수정하지 않는다. 동적 도구는 실험 API이므로 호환하지 않는 CLI는 실패 상태와 업데이트 안내로 처리한다.
- 엔진 도구는 현재 프로젝트·캔버스 세대(scope), InstanceId, 반영 전 필드 값, 소스 읽기 토큰을 확인한다. 씬 변경은 기존 커맨드를 사용한다. 소스는 기존 코드 문서에서 실행 취소·디스크 충돌 검사를 유지한다. 미저장 사용자 변경은 덮어쓰지 않는다.
- 가이드 YAML은 기존 파서·행동 표를 사용한다. 해석 실패는 기존 가이드를 바꾸지 않는다. 가이드의 질문 버튼으로 대화 패널을 열면 진행과 입력 제한을 일시정지하고, 계속하기/패널 닫기로 재개한다.
- 엔진에 `jbro-guide`, `jbro-create` 스킬을 함께 배포한다. 실행 중 카탈로그와 엔진 API를 읽고 행동을 조합한다. 지원하지 않는 드래그 안내·둘째 동종 컴포넌트 가이드·깊은 필드 등을 만들어내지 않는다.
- 프로젝트별 설정은 기존 사용자 환경설정 옆 별도 YAML에 프로젝트 경로·CLI 경로·대화 ID·선택 모델만 저장한다. 대화 복원 시 이전 작업을 재실행하지 않고 대상은 다시 조회한다.
- 대화 중단·연결 끊김·프로젝트/캔버스 전환 뒤 변경 호출은 재전송하지 않는다. 같은 callId는 한 번만 실행한다. 인증 없는 루프백 제어 포트에는 편집 기능을 추가하지 않는다.

## 검증 기록

### 연결과 자동 검증

- 설치된 `codex-cli 0.153.4`의 app-server 스키마와 실제 RPC를 대조했다. initialize → bundled skill extraRoots → account/read → model/list → thread/start + dynamicTools 교환이 성공했다. 모델과 도구 목록은 하드코딩하지 않는다.
- CLI 전역 기본 모델 `gpt-6.1-sol`은 현재 ChatGPT 인증에서 실제 추론이 거절됐다. 모델 카탈로그의 기본값을 명시적으로 선택하도록 수정한 뒤 `gpt-6-astra`로 실제 모델 턴이 성공했다. 카탈로그 조회만으로 추론 성공을 주장하지 않는다.
- 정식 `Agent` suite는 분할 UTF-8, 중복 호출, 중단 뒤 호출, 다른 프로젝트의 호출, 인증 실패의 키 비노출, 잘못된 JSON과 시작 타임아웃을 검사한다. 실제 에디터에서는 오브젝트 생성/실행 취소/다시 실행, 재생성 전 InstanceId의 무효화, 반영 전 값 검사, 컴포넌트 추가, 소스 저장/실행 취소/미저장 충돌, 경로 탈출 거절, 잘못된 가이드 거절, 공용 위젯의 패널 그리기를 검사한다.
- 번들 스킬 두 개는 실제 Codex `skills/list`에서 활성화되어 발견됐다. skill-creator의 Python 검사기는 `yaml` 모듈이 없어 실행하지 못했다. 이를 검사 통과로 세지 않으며 패키지를 추가 설치하지 않았다.
- 최종 Debug 호스트와 시험 실행 파일 빌드가 성공했다(`F:/AI/Temp/jbro-agent-final-debug-host2.log`, `jbro-agent-final-tests-build2.log`). 회귀 중 새 번역 키 선언 누락을 발견해 공용 `LocalizationKeys.h`의 상수와 두 로케일을 맞춘 뒤 다시 빌드했다.
- `F:/AI/Temp/jbro-agent-final-regressions2.log`: Agent, CodeEditor, EditorLocalization, EditorWidget, EditorGuideFocus, EditorGuide, EditorControlPort, EditorShortcut, ScriptProject, ScriptBuild **10 suites가 통과했다**. 러너의 11개 표시는 기본으로 건너뛴 AgentLive 1개를 포함한다. 실제 모델 검사는 아래의 별도 명시 실행이다.
- ScriptBuild 회귀는 의도한 미선언 식별자의 C2065 진단, 수정 뒤 빌드 성공과 프로젝트 종료 시 빌드 중단을 확인했다. 이것은 AI가 새 게임 기능을 작성·실행한 검증과 구분한다. 소스 충돌과 실행 취소는 Agent/CodeEditor 회귀의 범위다.
- 이전 Release 호스트 빌드 성공은 최종 대화 표시 보완 전 결과이며 최종 Release 검증으로 세지 않는다. 최종 구성 검증은 Debug에 한정한다. 새 공개 헤더의 독립 컴파일은 Debug 시험 빌드에 포함됐으며 모듈 의존 관계는 바꾸지 않았다.

### 실제 모델과 에디터 입력

`AgentLive`는 기본 실행에서 건너뛰며 `JBRO_AGENT_LIVE=1`로 명시적으로 실행해야 현재 Codex 계정으로 추론한다. `JBRO_AGENT_EVIDENCE`에 대화와 생성 YAML을 남긴다. 실행은 테스트용 프로젝트에서 하며 사용자 작업 프로젝트를 수정하지 않는다.

사용자가 지정한 세 문장을 그대로 보냈다.

## 후속

- 이미지 픽셀 첨부와 다른 AI 제공자는 후속이다. 에셋 드롭은 이미지를 모델에 보내는 기능과 구분한다.
- 지원되지 않는 가이드 행동은 본 작업에서 임의로 확장하지 않는다.

## 드래그 첨부 후속 (2026-10-16, 사용자 요청)

- AI 대화의 `끌어 놓아 첨부` 영역과 입력란에서 기존 `DragKind::Asset`, `HierarchyObject`, `InspectorComponent`를 받는다. 드래그 출처의 동작과 종류 문자열을 복제하지 않고 기존 DragDrop/AssetDrag 위젯을 사용한다.
- 인스펙터의 컴포넌트 꾸러미를 `Widget/ComponentDrag.h`로 공유한다. 기존 슬롯·목록 종류는 재정렬에 유지하고, 끌기 시작한 InstanceId를 함께 실어 AI 첨부가 다른 슬롯의 컴포넌트로 바뀌지 않게 한다.
- 에디터 번호를 현재 오브젝트의 InstanceId로 바꾸고 프로젝트·캔버스·세대를 기록한다. 컴포넌트/스크립트는 소유 오브젝트와 붙은 인스턴스 번호를 함께, 에셋은 AssetId를 저장한다. 표시 이름은 식별자가 아니다.
- 전송 전 목록에서 종류·이름·제거 단추와 무효 상태를 표시한다. 같은 대상은 중복하지 않고 한 턴에 16개까지 받는다. 선택 대상은 전송 시의 기존 자동 문맥으로 유지하되 명시 첨부를 별도 `attachments`로 전달한다.
- 삭제·캔버스 세대 변경·프로젝트 전환으로 무효가 된 첨부는 자동 교체하지 않는다. 무효 첨부를 제거하기 전에는 전송하지 않는다. 성공적으로 전송하면 대기 목록을 비우고 보낸 대화에 대상 이름과 식별자를 보존한다.
- 대화 표시에는 typed Target 배열을 사용하며 위젯이 JSON을 다시 해석하지 않는다. 복원한 문맥은 원본 JSON을 사용자 메시지로 표시하지 않고 이전 대상은 무효 상태로 되읽게 한다.
- `jbro_asset_read`는 현재 scope와 AssetId로 레지스트리의 경로·타입·소유 관계만 읽는다. 에셋 파일·픽셀을 통째로 보내거나 에셋을 이동·저장하지 않는다. 첨부만으로 씬 커맨드나 실행 취소 이력을 바꾸지 않는다.

### 첨부 참조의 수명 재검토 — 영속 조회 미구현 (2026-10-16)

사용자가 실행마다 바뀌는 InstanceId와 오브젝트·컴포넌트 GUID 부재를 지적했다. 앞선 보고는 식별자 종류만 설명하고 저장/재실행 수명과 선택 이유를 설명하지 않았다.

- 확인 사실: GameObject·ComponentBase·GameScriptBase에는 인스턴스 자체의 GUID 필드가 없다. InstanceRegistry는 InstanceId와 실행 중 핸들로 등록/조회하며 GUID 매핑도 GUID 조회 함수도 없다. 에셋의 AssetId와 구분한다.
- `CanvasFile::ReadObjects`는 `canvas.CreateObject(name)`과 `Attach(..., InvalidInstanceId)`로 오브젝트·컴포넌트를 다시 생성한다. 파일 안 오브젝트 번호와 컴포넌트 타입 내 순번으로 파일 내부 참조를 새 실행에 연결한다. 기존 실행의 InstanceId는 파일에서 복원하지 않는다. 실행 중 Undo/핫 리로드의 preferredId 복원과 디스크 재열기를 혼동하면 안 된다.
- 제공자의 thread/resume 처리는 이전 첨부의 revision을 0으로 바꿔 무효로 표시한다. 이는 오래된 대상의 사용을 막는 처리이며 같은 대상을 재발견하는 기능이 아니다. 현재 참조는 재시작뿐 아니라 캔버스 재로드 뒤에도 유지되는 영속 첨부가 아니다.
- 선택 근거: 승인 계획의 InstanceId 계약을 따라 기존 엔진 조회·편집 경로를 재사용했다. GUID를 기술적으로 사용할 수 없거나 성능 비교로 배제했다는 근거는 없다. 장기 대화의 참조 수명까지 해결한 설계로 보고한 것은 부정확했다. 기존 식별자를 재사용할 때 영속 조회가 없음을 먼저 알리고 설계를 검토해야 했다.
- 문서 불일치: ProjectRule §8.1의 예전 “영속 InstanceId”/“직렬화되는 값” 설명과 §6 후속 D-233·D-302 저장 규칙(InstanceId를 파일에 쓰지 않음)이 다르다. 현재 구현은 후자를 따른다. 예전 명칭으로 영속성을 주장하지 않는다. 이번 조사에서 저장 계약을 임의로 바꾸지는 않았다.
- GUID 도입을 선택한다면 단순 조회 함수 추가가 아니다. 인스턴스 GUID 부여·캔버스 저장/복원·GUID에서 현재 인스턴스로의 해석·복제 시 새 ID/Undo 시 원 ID·삭제/미저장 대상 수명을 함께 정해야 한다. 이는 아직 제안이며 구현/승인하지 않았다.

공통 위젯 대조: `Widget::TextButton`은 아이콘만 표시하는 단추의 명시 크기를 지원하므로 제거 단추를 큰 글자 Button으로 만든 것은 공통 위젯의 제약 때문이 아니다. `ListVirtual`은 참조 행의 데이터/표시를 분리해 재사용할 수 있다. 다만 현재 AgentHistory/AgentAttachments는 별도 테두리 영역과 고정 예약 높이여서 시안의 메시지·가이드 카드·하나의 입력 영역 구조와 다르다. 공통 위젯 계층 내부의 레이아웃/표현 보완이 필요하다. HTML의 색·본문/보조 글자 크기·SVG 아이콘도 EditorTheme·엔진 글꼴·기존 아이콘으로 검증한 상태가 아니다. 따라서 현재 시안을 공통 위젯만으로 이미 동일하게 구현할 수 있다고 보장하지 않는다. 승인 전 엔진 UI 수정 금지는 유지한다.

이번 확인은 소스·문서 대조다. 엔진 코드 수정·빌드·실제 재시작 시험·AI 호출은 수행하지 않았다.

스크립트 프로퍼티와 AI 첨부의 차이: `GetGameObjectHandleCodec`은 캔버스 저장 문맥에서 현재 InstanceId를 그 파일의 오브젝트 번호로 바꾸고, 로드 문맥에서 그 번호를 새 InstanceId로 해석한다. `CanvasFile`은 모든 오브젝트와 컴포넌트/스크립트를 먼저 만든 뒤, 같은 remap 문맥 안에서 스크립트에도 `ReadFields`를 적용한다. 컴포넌트 핸들은 파일 오브젝트 번호와 같은 타입 내 순번을 사용한다. 따라서 재실행 후 InstanceId가 바뀐다는 사실만으로 캔버스 내부의 스크립트 참조가 깨진다고 판단하면 안 된다. 다만 파일 밖 AI 대화의 과거 첨부에는 이 파일 저장 시의 번호 변환/로드 연결이나 별도 영속 식별자가 없다. 파일 안 번호를 AI의 영속 ID로 옮기는 것도 재저장 시 순서가 달라질 수 있어 해결책이 아니다. 이 구분은 소스 대조 결과이며 이번 질문에서 실행 시험은 하지 않았다.

### 구 엔진의 이진 GUID 최적화와 현 엔진의 차이 (2026-10-16)

사용자가 기억한 “GUID를 정수 둘로 관리”는 실제 구현이다. 구 엔진 `Engine/GameFramework/Object/GameInstance.h`는 오브젝트·컴포넌트 공통 기반에서 저장되는 `File::Guid m_instanceGuid`와 조회용 `Guid128 m_instanceGuid128`을 함께 보관하고 AssignInstanceGuid 한곳에서 동기화한다. `Engine/Utillity/File/Guid128.h`는 원래 GUID 128비트를 `uint64 Hi/Lo` 둘에 담고 파일 문자열과 왕복한다. 영속 GUID를 버리는 최적화가 아니다.

현 엔진은 D-9·D-10·D-20·D-26에서 인스턴스 식별/참조를 64비트 InstanceId와 핸들로 재설계했다. 생성기 이력은 2026-09-02 ce2ce974/2026-09-05 2fa5657c로 AI 첨부보다 앞선다. D-59는 실행 간 ID 신뢰가 필요하면 재검토하도록 범위를 제한했다. 별도 D-111(2026-09-18, ffdddb32)은 구 엔진의 문자열/이진 GUID 이중 보관을 없애고 `Uuid { UInt64 high, low; }` 하나로 에셋 영속 식별을 구현했다. 이진 GUID 타입이 없는 것이 아니라 현 인스턴스에는 부여하지 않은 것이다.

ProjectRule §8.1의 문자열 GUID 두 개 128B와 현 Ref 24B 비교는 구 엔진의 Guid128 조회 최적화까지 대조한 성능 검증이 아니다. 따라서 GUID를 쓰면 문자열 변환/비교가 필수라거나, GUID 영속성 제거가 필수 최적화였다고 설명하지 않는다. 현 저장 계약의 파일 내부 참조 복원과 외부 장기 식별은 별개다. 코사원은 구 엔진의 실제 최적화와 영속 참조 보존 여부를 먼저 비교했어야 했다. 이번에는 확인 내용만 기록하며 식별자·저장 계약·엔진 소스를 변경하지 않았다.

## 입력부 수정 (2026-10-17, 사용자 지시)

사용자가 자동 줄바꿈 누락, 파일 첨부로 보이는 +와 선택 대상 추가, 연결 전의 빈 모델 컨트롤을 지적하고 수정을 지시했다. HTML 최초 시안보다 이 후속 지시가 우선한다. GUID·엔진 도구·인증 프로토콜은 이번 범위에 넣지 않는다.
