# jbroc 컴파일러 규칙

> 2026-09-15 까지 논의한 **JBroScript 컴파일러 `jbroc`** 의 규칙을 모은 문서다. **렉서와 파서가 섰고(2026-09-17, §11) 타입체커·이미터는 아직 없다.**
> 사용자가 쓰는 문법은 [jbroscript-syntax.md](./jbroscript-syntax.md) 에 있다.
> 논의 과정과 실측 근거는 [jbroscript-plan.md](./jbroscript-plan.md)(§5·§13·§18·§20·§21)와
> [ide-plan.md](./ide-plan.md)(§4.1·§5.5)에 있고, 둘이 다르면 이 문서가 더 최근이다.

| 표시 | 뜻 |
|---|---|
| **[확정]** | 빡대리가 정했거나, 이미 실측으로 굳은 제약이다 |
| **[제안]** | 제안했고 아직 답을 받지 않았다 |
| **[열림]** | 결정이 필요하다. §10 에 모았다 |
| **[대기]** | 빡대리가 결정을 미뤘다 |

---

## 1. 무엇을 하는가 [확정]

`jbroc` 은 `.jscript` 를 **C++ 소스로 바꾸는 트랜스파일러**다. 그 뒤는 기존 C++ 스크립트와 같은 길이다.

```
Enemy.jscript  →  jbroc  →  Enemy.generated.h / Enemy.generated.cpp  →  MSVC  →  게임 DLL  →  호스트
```

`ScriptDLLLoader`·`ScriptRegistry`·스크립트 풀·핫 리로드는 그대로 쓴다. 이들 입장에서는 C++ 스크립트가 하나 더 생긴 것이다.

## 2. 구현 [확정]

| 항목 | 내용 |
|---|---|
| 언어 | **C++20**(MSVC), 엔진 리포 안의 실행 파일(엔진만 쓰는 Tier E 도구) |
| 모듈 | **`JBroScriptCompiler`**(정적 라이브러리, Tier E, `<JBro/ScriptCompiler/...>`)에 렉서·파서·타입체커·이미터를 두고, **`JBroc`**(실행 파일)은 명령줄만 맡는다. 테스트는 `JBroTests` 가 라이브러리를 참조한다(2026-09-17, D-104) |
| [제안] 문법 | 문법 문서의 [제안] 항목은 제안대로 파싱한다. 제안이 바뀌면 파서를 고친다(D-104) |
| 단계 | 렉서 → 파서 → 타입체커 → C++ 이미터 |
| 파싱 | **두 번 훑는다.** 먼저 모든 파일의 타입 이름을 모으고, 그다음 몸통을 읽는다. `var` 가 없어서 `float step = dt` 가 선언인지 알려면 `float` 이 타입인 것을 먼저 알아야 하고, `import` 없이 다른 파일의 타입이 보여야 하기 때문이다. **구현한 파서는 모양으로 갈라 한 번에 읽는다 - §11.2, 확인 대기** |
| 엔진 타입 정보 | 엔진의 리플렉션(`PropertyRegistry`)을 **링크해서** 빌트인 컴포넌트의 필드와 타입을 읽는다. 엔진 타입을 두 번째 파일에 다시 적지 않는다 |
| 편집기 | 같은 파서와 타입 정보를 `jbroc --lsp` 로 편집기에 준다. 편집기 쪽은 이 실행 파일을 띄우기만 한다(ide-plan P2) |

C++20 을 고른 이유는 엔진 리플렉션을 링크할 수 있고 툴체인이 늘지 않기 때문이다. 버린 안은 TypeScript(엔진 타입 정보를
다시 적어야 하고 엔진 설치에 Node 가 딸린다), Rust·C#(툴체인·런타임이 는다).
대가로 LSP 에 필요한 JSON 읽기·쓰기가 엔진에 없다. 필요해질 때 따로 정한다.

## 3. 타입체커

### 3.1 목표 [확정]

> **`jbroc` 이 에러 없이 통과시킨 `.jscript` 는, 생성 C++ 가 `/W4` 에서 경고도 에러도 없이 컴파일된다.**

MSVC 가 무엇이든 말하면 그것은 `jbroc` 의 결함이다. 사용자는 C++ 에러 메시지를 보지 않아야 한다.

### 3.2 잡는 것

| 검사 | 상태 | 예 |
|---|---|---|
| 이름 해석(없는 필드·함수·타입), 중복 선언 | [확정] | `target.Destory()` |
| 타입 불일치, 인자 개수·타입 | [확정] | `Int x = "a"` |
| **스크립트에 없는 타입 이름** | [확정] | `int`, `float`, `bool`, `double`, `int32`. 엔진에 있는 `Int32`·`UInt` 도 스크립트에는 없다 |
| **값이 손실될 수 있는 숫자 변환을 명시 없이 씀** | [확정] | `Int cells = width / size`(`Float` → `Int`), `Float x = someInt`(`Int` 64비트 → `Float` 32비트) |
| 반환 타입과 `return` 불일치, 반환값이 필요한데 끝에 닿는 함수 | [확정] | `fn F() -> Int { }` |
| 필드 타입 생략 | [확정] | `public MyInt = 1` |
| **`ref` 매개변수에 넘기면서 호출하는 쪽에 `ref` 를 빠뜨림** | [확정] | `Raycast(from, down, 1.0, hit)` |
| **`if`·`else if`·`for`·`while`·`switch` 의 조건 괄호 누락** | [확정] | `if hp <= 0` |
| `if let`, `do`–`while`, `goto`, 이름 붙인 `break` | [확정] | 문법에 없다 |
| **다이아몬드 상속**(`interface` 는 예외) | [확정] | §5.3 |
| `script` 가 `script` 를 둘 이상 상속 | [확정] | 엔진 베이스가 두 경로로 닿는다 |
| **JBroScript 키워드를 이름으로 사용** | [확정] | 필드 이름 `fn`, `ref`, `while`. **C++ 키워드(`new`·`template` 등)는 거절하지 않는다**(§5.5) |
| `callback` 함수의 이름·인자가 엔진 훅 목록에 없음 | [확정] | `fn OnTick() callback`(엔진 훅은 `OnUpdate`) |
| `override` 인데 부모에 그런 가상 함수가 없음 | [확정] | |
| `require` 가 남은 채 인스턴스로 쓰는 타입 | [확정] | 순수 가상 함수를 구현하지 않은 `class` 를 값으로 선언 |
| 선언 종류 규칙 위반 | [확정] | `script` 를 값으로 선언, `struct` 에 생성자 |
| `static`·`const` 가 붙을 수 없는 자리 | [확정] | 전역 함수, const 멤버 함수 |
| 필드 어트리뷰트: 모르는 이름, 인자 개수·타입 | [확정] | `[rnage(0, 1)]` |
| 스크립트에서 **읽기만** 허용한 엔진 필드에 쓰기 | [확정] | `Transform2D` 의 월드 캐시(`worldPosition` 등). 인스펙터의 `ReadOnly` 와 뜻이 다르므로 그것을 빌려 쓰지 않는다 |
| 지역 변수를 초기화 없이 선언 | [제안] | 컨테이너와 값 타입의 기본값은 예외. 흐름 분석 없이 "초기화하지 않은 변수" 가 사라진다 |
| enum `switch` 에서 빠진 값(그리고 `default` 없음) | [제안] | |
| 컨테이너를 순회하는 도중 원소를 더하거나 빼기 | [제안] | |

잡지 않는 것: 쓰지 않는 변수, 도달하지 않는 코드, 0 나누기, 무한 루프.

### 3.3 진단 메시지 [확정]

- 메시지는 **문장이 아니라 키**로 들고 있다가 언어를 골라 낸다. 편집기가 LSP 초기화 때 넘기는 `locale` 을 쓰고,
  그 언어가 없으면 영어를 낸다(ide-plan §5.5). 명령줄로 돌릴 때도 같은 메시지 표를 쓴다.
- 편집기 확장은 이 메시지를 그대로 보여 주기만 한다.
- **번역 표는 `Localization/jbroc/<로케일>.yaml` 이다**(2026-09-17, D-104). 파일 모양과 로케일 이름(`ko-KR`·`en-US`)은
  에디터의 `Localization/<로케일>.yaml` 과 같고, `jbroc` 이 JBroCore 의 `Yaml.h` 로 직접 읽는다.
  에디터의 `LocalizationTable` 은 `JBroEditor` 안에 있어 쓸 수 없다.

## 4. `ref` 를 무엇으로 바꾸는가 [열림]

문법에서 `ref` 는 **단순한 포인터**이고 매개변수·멤버·지역 어디에나 쓴다(syntax §8.1).
자동 null 검사가 댕글링을 막으려면 **대상이 사라질 때 `ref` 가 스스로 null 이 되는 C++ 타입**이어야 한다.
원시 포인터는 대상이 파괴되어도 null 이 되지 않는다.

**[제안]** 대상에 따라 고른다.

| `ref` 의 대상 | C++ | 스스로 null 이 되나 | 근거 |
|---|---|---|---|
| `script`, 빌트인 컴포넌트 | `Ref<T>`(24B) | 된다 | 영속 참조, 저장·핫 리로드를 넘는다(`ProjectRule.md` §6) |
| 게임 오브젝트 | `GameObjectHandle`(16B) | 된다 | 같다 |
| `OwnerPtr` 로 소유된 `class` | `SafePtr<T>` | 된다 | 엔진의 비소유 참조 규칙 |
| 다른 객체 안에 값으로 들어 있는 `class` | — | **안 된다** | `SafePtr` 의 제어 블록은 `OwnerPtr`·풀에서만 생긴다(`SafePtr.h:127-135`) |
| 값(`Int`, `Float`, `struct`), 컨테이너 원소 | `T*` | **안 된다** | 원시 포인터밖에 없다 |
| `ref` 매개변수(값 대상) | `T&` 또는 `T*` | — | 한 콜백 안에서만 산다 |

- **매개변수·지역**의 원시 포인터는 안전하다. 엔진이 파괴를 콜백 뒤로 미루기 때문이다(D-45).
  단 **컨테이너 원소를 가리키면** 같은 함수 안에서도 컨테이너가 커질 때 끊긴다.
- **멤버**로 "안 된다" 줄을 들고 있으면 `ProjectRule.md` §6 의 MUST("스크립트가 대상의 수명 밖까지 보관하는 멤버에는
  raw pointer 를 저장하지 않는다")와 부딪힌다. 허용하려면 그 규칙을 함께 고쳐야 한다(§10 의 1번).

## 5. 이미터

### 5.1 디버깅을 위한 제약 [확정]

실측으로 굳은 것이다(jbroscript-plan §18). 셋을 지키면 Visual Studio 에서 지역 변수·콜스택·스텝이 스크립트처럼 보인다.

1. **문장마다 `#line` 을 다시 찍는다.** 블록 앞에 한 번은 모자라다. 생성 C++ 의 줄 수가 원문과 다르면 중단점이 옆 줄에 선다.
2. **이름을 1:1 로 유지한다.** `speed` 는 `speed`, `fn OnUpdate` 는 `OnUpdate`. 예외는 C++ 에서 그대로 쓸 수 없는 이름뿐이다(§5.5).
3. **임시변수를 만들지 않는다.** 식을 그대로 옮긴다. 공통부분식 제거 같은 최적화는 MSVC 에 맡긴다.

그래서 연산자 우선순위를 C++ 과 같게 두었다(syntax §10.1). 괄호를 새로 넣거나 식을 쪼갤 일이 없다.

### 5.2 문법 → C++

| 문법 | C++ | 상태 |
|---|---|---|
| `Int`, `Float`, `Bool`, `String` | 엔진 타입 그대로(`JBro::Int` 는 `Int64` 의 별칭, `JBro::Float` 은 `float` 을 감싼 클래스) | [확정] |
| `Vector2` | 엔진 타입 그대로. 엔진 이름을 `Vec2` → `Vector2` 로 바꾸기로 했고 아직 바꾸지 않았다(§9) | [확정] |
| `0.5` | `0.5f` | [확정] |
| `and` / `or` / `not` | `&&` / `\|\|` / `!` | [확정] |
| `Int(x)`, `Float(x)` | 엔진 타입의 명시 생성(안쪽은 `static_cast`) | [확정] |
| `ref hit`(호출하는 쪽) | 매개변수의 C++ 모양(§4)에 맞춰 넘긴다 | [확정] |
| `if (...)`, `while (...)`, `switch (...)`, `else` | 같은 C++ 문 | [확정] |
| `fn Name(...) -> T` | `T Name(...)` | [확정] |
| `callback` | 엔진 훅의 `override` | [확정] |
| `override` / `require` | `override` / `= 0` | [확정] |
| 접근자 `public` 등 | 멤버마다 C++ 접근 구역으로 | [확정] |
| 스크립트 `enum` | `enum class` + 리플렉션의 enum 이름 설명자 | [확정] |
| 프로퍼티 필드 | `PropertyInfo`. 스크립트 보관함(DLL 수명)에 등록한다(jbroscript-plan §8.4) | [확정] |
| `is null` / `is not null` | `== nullptr` / `!= nullptr`(또는 핸들의 무효 검사) | [제안] |
| `for (i in 0..n)` | `for (Int i = 0; i < n; ++i)` | [제안] |
| `for (ref e in arr)` | 범위 기반 `for` 와 참조 | [제안] |
| `switch` | 떨어짐 없는 `switch`, `case` 마다 `break` | [제안] |

### 5.3 상속 [확정]

- **다이아몬드 검사는 `jbroc` 이 한다.** 모든 타입을 먼저 훑었으므로 상속 그래프 전체를 안다. 어떤 타입의 조상 중에
  **`interface` 가 아닌 타입이 두 경로로 닿으면** 그 선언에서 에러를 낸다. C++ 컴파일러에 맡기면 안 된다.
  비가상 다이아몬드는 선언만으로는 C++ 에러가 아니고, 모호한 멤버에 접근할 때 비로소 사용자가 쓰지 않은 코드의 말로 에러가 난다.
- **`interface` 상속은 C++ 가상 상속(`virtual public`)으로 내린다.** `interface` 다이아몬드를 허용하므로, 비가상으로 내리면
  `I` 로 바꾸는 순간 C++ 이 모호성 에러를 낸다. `interface` 는 상태가 없어 대가가 작다.
- 그래서 **`interface` → 구체 타입 내림 변환은 v1 에 없다.** 가상 기반에서는 `static_cast` 가 안 되고, `dynamic_cast` 는
  매 프레임 경로에서 금지다(`ProjectRule.md` §9).
- **엔진 베이스를 C++ 부모 목록의 맨 앞에 둔다.** 스크립트 레지스트리는 `static_cast` 로 주소를 보정하므로
  (`ScriptRegistry.h:83`) 순서가 달라도 생성·파괴는 맞게 돌지만, 풀이 주소로 슬롯을 찾는 길이 부모 순서에 기대는지는
  확인하지 않았다. 앞에 두면 그 질문이 없다.
- `script` 에 부모를 적지 않으면 프로젝트 차원의 엔진 베이스(`GameScript2D` 등)를 붙인다.

### 5.4 자동 null 검사

문법의 `autochecknullable`(syntax §9.2)을 내리는 방식이다.

**[확정]** `ref` 를 쓰는 문장을 `if` 로 감싸고, null 이면 걸러서 **에러 로그**를 남긴다. 값이 필요한 자리도 같다.
**한 문장에 `ref` 가 둘 이상이면 모두를 한 조건으로** 검사한다.

```
// Enemy.jscript                             // 생성 C++ (모양만 보인다)
target.position.x += 1.0                     if (target != nullptr) { target->position.x += 1.0f; } else { /* 에러 로그 */ }
target.position.y = enemy.GetHeight()        if (target != nullptr && enemy != nullptr) { target->position.y = enemy->GetHeight(); } else { /* 에러 로그 */ }
Float hp = enemy.GetHp()                     Float hp; if (enemy != nullptr) { hp = enemy->GetHp(); } else { /* 에러 로그 */ }
```

- **선언은 `if` 밖에 남긴다.** 안에 두면 C++ 에서 변수의 범위가 `if` 블록으로 줄어 다음 줄에서 쓸 수 없다.
  그래서 걸러진 경우 변수는 **기본값**으로 남는다(syntax §12 의 4번).
- **[제안]** 에러 로그는 **null 인 `ref` 마다** 남긴다. `else` 쪽에서 각 `ref` 를 다시 검사하면 어느 것이 null 이었는지 알 수 있고, 임시변수가 필요 없다.
- **[제안]** 로그는 **호출 위치마다 한 번**만 남긴다. 매 프레임 경로에서 문자열을 만들면 안 되므로(`ProjectRule.md` §9)
  고정 문자열과 위치 번호만 넘긴다.
- **[제안]** 대상은 **두 번 해석**한다(조건에서 한 번, 본문에서 한 번). `Ref<T>` 의 해석은 캐시 비교라 싸다.
  `if (T* p = target.Get())` 로 한 번만 하면 지역 변수 `p` 가 디버거에 떠서 §5.1 의 3번과 부딪힌다.
- 자동 검사를 끈 `ref` 는 `target->Func()` 로 바로 내린다. `Ref<T>::operator->` 는 Debug 에서 단언한다(`Ref.h:82`).
- **[열림]** `return`·`if` 조건·`while` 조건처럼 **문장을 통째로 거르면 뜻이 달라지는 자리**의 규칙(syntax §12 의 4번).

### 5.5 C++ 에서 쓸 수 없는 이름은 바꿔 쓴다

**[확정]** 스크립트가 예약하는 것은 **JBroScript 자체의 키워드뿐**이다(syntax §2.1). `template`·`new`·`delete` 처럼
JBroScript 에서는 문제없지만 C++ 에서 쓸 수 없는 이름은, 사용자에게 금지하지 않고 **이미터가 그 이름만 바꿔 내린다.**

```
// jscript                          // 생성 C++
String template                     String jbro_gen_template;
Int delete = 0                      Int jbro_gen_delete = 0;
```

- **이유**: 사용자는 C++ 가 아니라 JBroScript 를 쓴다. C++ 키워드 수십 개를 금지하는 것은 "C++ 특유의 지식을 강요하지 않는다"(syntax §1)와 정면으로 부딪힌다.
  §5.1 의 이름 1:1 원칙은 디버깅을 위한 것이라, 극히 일부 이름만 예외로 두는 대가가 금지보다 작다.
- **원래 이름이 쓰이는 곳**: 리플렉션(`PropertyInfo` 의 이름 `"template"`), 저장 파일, 인스펙터, 진단 메시지, LSP(자동완성·정의로 이동).
- **바뀐 이름이 보이는 곳**: 디버거(지역 변수 창·조사식)뿐이다. 조사식에는 바뀐 이름을 쳐야 한다.

**[제안]** 바꾸는 규칙의 세부:

- **바꾸는 대상**은 "C++ 에서 그 이름 그대로 쓸 수 없거나 위험한 이름" 전부다. 키워드만으로는 모자라다.
  - C++ 키워드(`new`, `delete`, `template`, `default`, `operator`, `this`, `virtual` …)
  - C++ 대체 토큰(`xor`, `bitand`, `bitor`, `compl`, `not_eq`, `and_eq`, `or_eq`, `xor_eq`). `and`·`or`·`not` 은 JBroScript 키워드라 이미 이름이 될 수 없다
  - C++ 가 구현용으로 예약한 모양(`__` 가 들어간 이름, `_` 뒤에 대문자로 시작하는 이름)
  - 스크립트가 보지 못하는 엔진 베이스 클래스 멤버와 겹치는 이름(예: `ComponentBase::GetTypeId`). 겹치면 C++ 에서 부모 멤버가 가려진다
- **바꾼 이름이 사용자 이름과 겹치지 않게 한다.** 사용자 이름이 `jbro_gen_` 으로 시작하면 그것도 바꾼다
  (`jbro_gen_x` → `jbro_gen_jbro_gen_x`). 그러면 바꾸는 규칙이 일대일이 되어 **접두사를 예약하지 않아도** 겹칠 수 없다.
- **이미터가 스스로 만드는 이름도 전부 `jbro_gen_` 으로 시작한다.** 위 규칙 덕분에 사용자 이름과 겹칠 수 없다.
- **스크립트 필드 등록에 `JBRO_REFLECT_BODY`·`JBRO_FIELD` 매크로를 쓰지 않는다.** 두 이유가 있다.
  ① `JBRO_FIELD` 는 필드 이름을 **멤버 이름에서 뽑는다**(`Field.h:393-401`, jbroscript-plan §14.2). 멤버가 `jbro_gen_template` 이면
  등록 이름도 그렇게 된다. ② 그 매크로는 필드를 **`public` 으로 만든다**. 스크립트는 `private` 프로퍼티가 있다(syntax §4.3).
  그리고 매크로가 클래스 안에 넣는 `JBroSelf`·`JBroFieldBase`·`JBroFieldAt` 은 사용자 이름과 겹칠 수 있다.
  그래서 `jbroc` 은 `PropertyInfo` 를 **원래 이름을 적어서 직접 생성한다.** 원래 계획(jbroscript-plan §7.3 "생산자 둘")과도 같다.
- 스크립트가 거쳐 가는 엔진 공개 헤더에 매크로 이름이 섞이면(`windows.h` 의 `DELETE`·`near` 같은 것) 그 이름도 바꿔야 한다.
  2026-09-15 기준 스크립트 공개 헤더(`JBroCore`·`JBroRuntime`·`JBroFramework2D`·`JBroAssetTypes`)에는 `windows.h` 가 없다.
  **테스트로 붙잡는다**(§8).

## 6. 빌드 [확정]

- **`.jscript` 하나당 생성 `.cpp` 하나.** 한 파일에 몰면 한 줄 고칠 때마다 전체를 다시 컴파일한다.
- **내용이 바뀌지 않았으면 생성 파일을 덮어쓰지 않는다.** 그래야 MSVC 가 재컴파일을 건너뛴다.
- **실제로 쓰는 타입만 `#include` 한다.** 문법에 `import` 는 없고 프로젝트 전체의 타입이 보이지만, C++ 로 바꿀 때는
  그 파일이 실제로 쓰는 타입의 헤더만 넣는다.
- **생성 헤더에는 전방 선언만 둔다.** 다른 스크립트의 헤더 `#include` 는 생성 `.cpp` 에 둔다. 실행 성능은 같고,
  이렇게 해야 한 스크립트를 고쳤을 때 재컴파일이 번지지 않는다. 값으로 담는 타입처럼 크기를 알아야 하는 경우만 헤더에 넣는다.
- 편집기의 "빌드" 는 `jbroc` → MSBuild 를 부르는 일이다. 생성 C++ 의 MSVC 에러는 `#line` 덕분에 `.jscript` 줄을 가리키므로
  편집기의 `$msCompile` 매처로 받을 수 있다(ide-plan §6 P0).

| 함수(`Destroy`, `GetComponent<T>`, `Raycast`, 엔진 훅) | 리플렉션에 함수가 없으므로 엔진 쪽에 **"스크립트가 부를 수 있는 함수" 선언 표**를 두고, 표의 모든 항목을 부르는 C++ 를 생성해 컴파일하는 테스트로 실제 코드와 맞춘다 | **[대기]** |

버린 안: C++ 헤더를 파싱(기존 엔진이 정규식으로 `JPROP` 을 읽다 실패한 길), 별도 문서 파일만 두기(C++ 와 어긋나도 잡을 수 없다),
엔진 함수 호출은 검사하지 않고 MSVC 에 맡기기(§3.1 목표를 어긴다).

### 7.1 함수 시그니처를 스크립트 표기로 자동 변환할 수 있는가 (2026-09-15 프로브)

**된다. 매개변수 타입과 반환형은 컴파일러가 뽑고, 스크립트 표기로 바꾸는 것은 기계적이다.**
선언 표를 정하는 결정(위 표의 [대기])은 그대로이고, 여기 적는 것은 그 표를 만드는 방법을 잰 결과다.

**잰 방법**: 실제 엔진 공개 헤더(`<JBro/ScriptAPI.h>`)를 include 하고, 멤버 함수 포인터의 타입(`decltype(&C::F)`)을
템플릿으로 풀어 매개변수·반환 타입을 꺼낸 뒤 C++ 타입 → 스크립트 이름 표로 바꿨다. MSVC 19.51, `/std:c++20 /W4`.
`decltype` 만 쓰므로 엔진 함수를 부르지 않고, 엔진 라이브러리를 링크하지 않아도 된다. **경고 0개로 컴파일되고 돌았다.**
프로브는 세션 스크래치패드에 있었고 커밋하지 않았다(이 절의 설명으로 다시 만들 수 있다).

| 엔진 C++ | 자동 변환 결과 |
|---|---|
| `bool Physics2DService::Raycast(Vec2, Vec2, float, Collision2D&) const` | `fn Raycast(Vector2, Vector2, Float, ref Collision2D) -> Bool` |
| `void Physics2DService::OverlapBox(const Rect&, Array<GameObjectHandle>&) const` | `fn OverlapBox(Rect, ref Array<ref GameObject>)` |
| `void GameObjectHandle::Destroy()` | `fn Destroy()` |
| `void GameObjectHandle::SetActive(bool)` | `fn SetActive(Bool)` |
| `bool GameObjectHandle::IsActive() const` | `fn IsActive() -> Bool` |
| `Float Float::Clamp(float, float) const` | `fn Clamp(Float, Float) -> Float` |
| `SizeType Array::Size() const noexcept` | `fn Size() -> Int` |

쓴 변환 규칙:

| C++ | 스크립트 |
|---|---|
| `bool` / `float`, `JBro::Float` | `Bool` / `Float` |
| `int32`, `int64`, `std::size_t` | `Int`(손실 없는 넓힘. 크기는 투영이 정한다, syntax §10.3) |
| `Vec2` | `Vector2`(엔진 이름을 바꾸기로 했다. 바뀌면 이 줄은 필요 없다) |
| `const T&` 매개변수 | `T` |
| `T&` 매개변수(const 아님) | `ref T` |
| `Ref<T>` / `GameObjectHandle` | `ref T` / `ref GameObject` |
| `void` 반환 | `->` 없음 |

**자동으로 안 되는 것**(프로브에서 실제로 걸린 것):

1. **매개변수 이름.** C++ 함수 타입에는 `origin`·`direction` 같은 이름이 없다. 편집기 호버에 이름을 보이려면 사람이 적는다.
2. **같은 이름의 오버로드.** `Float::Clamp` 는 멤버와 static 이 같은 이름이라 `decltype(&Float::Clamp)` 가
   컴파일 에러(C3556)였다. 타입을 적어 하나를 골라야 했다. 스크립트에 오버로드를 둘지는 아직 정하지 않았다.
3. **기본 인자.** 함수 타입에 담기지 않아 사라진다.
4. **`noexcept`·`const` 조합.** 함수 타입의 일부라 변환 규칙에 조합마다 한 번씩 적어야 한다(한 번 적으면 끝이다).
5. **이름이 없는 타입은 바로 드러난다.** 컴포넌트 이름을 표에 넣지 않았더니 `GetComponent<Transform2D>` 가
   `ref <unmapped>` 로 나왔다. 실제 구현에서는 이것을 **컴파일 에러로** 만들면, 스크립트 이름이 없는 엔진 타입을 API 에 내놓는 순간 빌드가 멈춘다.

**그래서 선언 표를 만든다면 이런 모양이 된다**([제안], 결정은 [대기]):

```cpp
JBRO_SCRIPT_API(Service::Physics2DService, Raycast, "origin", "direction", "distance", "hit");
```

- 타입은 컴파일러가 뽑는다. 사람은 **매개변수 이름만** 적는다. 이름 개수가 매개변수 개수와 다르면 컴파일 에러다.
- `jbroc` 은 이 표로 타입을 검사하고, `jbroc --lsp` 는 호버에
  `fn Raycast(Vector2 origin, Vector2 direction, Float distance, ref Collision2D hit) -> Bool` 을 보인다. **편집기 확장 쪽 일은 없다.**
- 오버로드는 표에 적을 때 타입으로 하나를 고른다.

## 8. 테스트 [확정]

- **`.jscript` 표본 모음**을 두고, 생성 C++ 를 `/W4` 로 컴파일해 경고·에러가 0 인지 본다.
- **거절 표본**도 둔다. 타입 에러가 있는 표본은 `jbroc` 이 **거절해야** 통과한다. 거절 표본이 없으면 무엇이든 받아들이는 `jbroc` 이 통과한다.
- 디버그 매핑은 PDB 에 직접 물어서 잰다(`SymGetLineFromAddr64`, jbroscript-plan §13.3.1·§18.2). 표본의 문장 줄과 PDB 의 줄이 같아야 한다.
- 진단 메시지는 `ko` 와 `en` 으로 각각 받아 **서로 다른지** 본다. 한쪽만 보면 번역이 아예 안 되어도 통과한다.
- **이름 바꾸기**(§5.5): C++ 키워드·대체 토큰·예약 모양·`jbro_gen_` 으로 시작하는 이름을 필드·함수·enum 멤버·지역 변수로 쓴 표본이
  `/W4` 로 컴파일되고, 저장→로드에서 **원래 이름**으로 남고, 다른 스크립트가 그 멤버에 닿는지 본다.
  `jbro_gen_x` 와 `x` 를 한 타입에 함께 둔 표본으로 겹침이 없는지 본다.
- 스크립트 공개 헤더를 include 한 뒤 **알려진 매크로 이름이 정의되어 있지 않은지** 컴파일 타임에 확인하는 표본을 둔다
  (`#ifdef DELETE` 류). 누가 공개 헤더에 `windows.h` 를 끌어오면 여기서 먼저 멈춘다.

   자동 null 검사로 댕글링을 막을 수 없다. 금지하거나, 허용하되 경고하거나, 엔진에 새 제어 블록 길을 만든다.
2. ~~엔진의 `Vec2` 를 `Vector2` 로 바꾸는가~~ **바꾼다(2026-09-15 확정).** 이름 변경 작업만 남았다(§9).
3. ~~엔진 API 의 `Int32`·`UInt` 반환~~ **손실 없는 넓힘은 투영이 저절로(2026-09-15).** 컨테이너 크기를 `Int` 로 돌려주는 것만 [제안](§9).

6. **엔진 함수 선언 표**(§7). 빡대리가 결정을 미뤘다.
7. **이름 바꾸기의 세부**(§5.5 의 [제안] 목록). 방향은 확정이다.

## 11. 구현 현황

**아래는 코드가 선 것이다.** 규칙의 원문은 위의 절들이고, 여기에는 구현하면서 정한 세부와 잰 결과를 적는다.

### 11.1 렉서 (2026-09-17)

`Modules/JBroScriptCompiler`(D-104)의 `Lex()` 다. 원문 → 토큰 열이고, 에러가 있어도 끝까지 자른다(편집기는 한 파일의 에러를 모두 보여야 한다).

문법 문서가 정하지 않아 **구현하면서 정한 것**:

| 항목 | 정한 것 | 이유 |
|---|---|---|
| 줄바꿈 | 연속된 줄바꿈과 파일 맨 앞의 줄바꿈은 문장 끝 하나로 모으거나 내지 않는다. `( )`·`[ ]` 안에서는 내지 않는다(D-104) | 파서가 빈 줄을 셀 이유가 없다 |
| 닫지 않은 괄호 | `{`·`}` 를 만나면 괄호 깊이를 0 으로 되돌린다 | 이 언어는 괄호 안에 중괄호가 오지 않는다. 되돌리지 않으면 `if (a` 한 줄의 실수가 파일 끝까지 줄바꿈을 먹어 파서가 한 문장으로 읽는다 |
| 숫자 | `20`·`0.5` 두 모양. 점 뒤에 숫자가 있어야 실수다(`0..n` 은 정수와 범위). 16진수·지수 표기는 없다 | 문법 §10.2 가 두 모양만 적었다 |
| 숫자에 붙은 글자 | `10f`·`2D` 는 **한 토큰**으로 읽고 에러 | 둘로 자르면 에러가 `f` 나 `D` 를 가리킨다 |
| 정수 범위 | 64비트 부호 있는 정수에 들어가야 한다 | `Int` 가 64비트다(문법 §7.1) |
| 문자열 | 이스케이프는 `\"`·`\`·`\n`·`\t` 뿐. 줄이 바뀌기 전에 닫혀야 한다 | 줄을 넘는 문자열은 문법에 없다 |
| 이름 | ASCII 글자·숫자·`_` | C++ 이름으로 1:1 로 내린다(§5.1). 한글은 문자열과 주석 안에서만 쓴다 |
| 모르는 글자 | UTF-8 한 글자를 통째로 에러 하나로 | 바이트마다 에러를 내면 한글 한 글자가 에러 세 개가 된다 |
| `&&`·`\|\|`·`!` | "`and`·`or`·`not` 을 쓰라" 는 전용 에러 | C 계열에서 넘어온 사람이 가장 흔히 할 실수다 |
| `>>` | `>` 두 개 | 시프트 연산자가 없으므로 `Array<Table<String, Int>>` 가 저절로 맞다 |
| 열 번호 | UTF-8 바이트 단위, 1 부터 | 이름이 ASCII 라 코드의 열은 글자 수와 같다. LSP 는 UTF-16 단위라 `--lsp` 에서 바꾼다 |
| BOM | 파일 맨 앞의 UTF-8 BOM 은 건너뛰고 열도 밀지 않는다 | 엔진의 한글 소스 규칙(BOM)대로 저장된 `.jscript` 가 흔하다 |

**진단 메시지**: 키 여섯 개(`jbroc.lex.*`)와 `Localization/jbroc/ko-KR.yaml`·`en-US.yaml`. 읽는 코드는 `DiagnosticMessages` 이고
현재 로케일 → 폴백 → 키 그대로 순이다. 엔진의 YAML 은 바깥 따옴표만 벗기고 이스케이프를 풀지 않으므로, 메시지 안의 `\n` 은
두 글자 그대로 나온다.

**검증.**

- `Tests/ScriptCompilerLexerTests.cpp`. 규칙마다 틀렸을 때 달라지는 입력을 둔다. 두 로케일 표가 모든 진단 키를 채우고
  **두 언어의 글이 서로 다른지**, 표에 쓰이지 않는 키가 없는지 본다(§8).
- 컴파일러 테스트는 `TestMain` 맨 앞에서 돈다. 그래픽이 없어 몇 초 안에 끝나므로, 틀렸을 때 뒤의 긴 테스트(전체 약 160초)를 기다리지 않는다.
- **음성 테스트**: `JBroScriptCompiler` 소스가 의존하지 않은 `<JBro/Runtime/GameObject.h>` 를 include 하면 C1083, `JBroCore` 소스가
  `<JBro/ScriptCompiler/Lexer.h>` 를 include 하면 C1083 인 것을 빌드로 확인했다(시험 파일은 지웠다).

**뮤테이션(2026-09-17).** 렉서·진단 표에 변이 27개를 넣었다. 처음 돌렸을 때 23개를 잡았고 넷이 남았다.

- `\r` 을 공백으로 넘기지 않는 변이가 살았다. `\r` 이 "모르는 글자" 에러만 내고 토큰은 만들지 않아 **토큰 열이 같았고**,
  CRLF 테스트는 토큰 열만 봤다. 테스트 구멍이라 에러 수를 함께 보게 고쳤다(`6d05d43`).
- `IsKeyword` 의 범위를 줄인 변이가 살았다. 부르는 곳이 없는 함수라 잡을 방법이 없었다. 테스트를 지어내지 않고 함수를 지웠다.
- 둘은 도구가 건너뛰었다. `tools/mutate.py` 는 목록의 `\n` 두 글자를 줄바꿈으로 바꾸므로, C++ 소스의 `'\n'` 을 찾는 변이는
  글이 어긋난다. 같은 동작을 `\n` 글자가 없는 자리에서 겨누도록 바꿔 다시 돌렸다.

고친 뒤 남은 셋을 다시 돌려 **셋 다 잡았다.** 의미 있는 변이 26개를 모두 잡는다. 전체 `JBroTests` 가 약 160초라
도구의 제한 시간(180초)에 여유가 없어서, 도구 파일은 고치지 않고 제한 시간만 420초로 바꿔 읽어 들여 돌렸다.

### 11.2 파서 (2026-09-17)

`Parse()` 가 파일 하나를 구문 트리(`SyntaxTree`)로 읽는다. 렉서도 안에서 부른다.

**트리 모양.** 노드는 포인터가 아니라 **번호**로 가리킨다. 노드가 배열 하나에, 자식 번호가 배열 하나에 있다. 노드 종류마다 자식
자리가 정해져 있고 빈 자리는 `InvalidNode` 다(`SyntaxTree.h` 의 `SyntaxKind` 옆에 자리를 적었다). 이름·연산자·리터럴은 원문을
가리키는 `std::string_view` 다. 테스트와 앞으로의 `jbroc --dump-tree` 는 들여쓴 덤프 글(`DumpSyntaxTree`)로 비교한다.

**구현하면서 정한 것:**

| 항목 | 정한 것 | 이유 |
|---|---|---|
| **선언과 식을 가르는 법** | **모양으로 가른다.** 문장이 "타입 + 이름" 으로 시작하면(`Collision2D hit`, `Array<ref Enemy> allies`, `ref Enemy nearest`) 선언이다 | 이 언어의 식에는 이름 두 개가 나란히 오는 모양이 없다. `Name <` 로 시작하면 타입으로 읽어 보고, 실패하면 식이다(읽어 본 노드는 버린다) |
| 제네릭 호출 | `Name<` 뒤가 타입 인자로 읽히고 `>` 바로 뒤에 `(` 가 오면 제네릭 호출(`GetComponent<Transform2D>()`) | 비교 연산의 연쇄 `a < b > (c)` 는 `Bool` 과 수의 비교라 어차피 타입 에러다 |
| 문맥 키워드 | `callback`·`override`·`require` 는 함수 선언의 `)`·반환 타입 뒤에서만, `in` 은 `for (` 의 변수 뒤에서만 키워드로 본다 | 문법 §2.1 |
| 본문 위치 | `{` 는 다음 줄에 와도 된다. 함수 선언 뒤에 `{` 가 없으면 선언만 있는 함수다(interface·require) | 엔진 코드 스타일(중괄호를 다음 줄에)과 같다 |
| `else` | 앞 블록 다음 줄에 올 수 있다. `else` 가 없으면 줄바꿈을 먹지 않고 되돌린다 | 그 줄바꿈이 if 문의 끝이다 |
| 범위 `..` | 식 우선순위표(문법 §10.1)보다 한 단계 낮다 | `0..table.Size()` 가 저절로 맞다 |
| 에러 복구 | 문장·멤버마다 첫 에러만 내고, 줄 끝이나 `}` 까지 건너뛴 뒤 다시 읽는다. 선언 밖의 쓰레기는 줄을 여는 선언 키워드까지 건너뛴다 | 괄호 하나가 에러 열 개가 되지 않게, 다음 문장의 진짜 에러는 놓치지 않게 |

파서가 내는 진단은 14개(`jbroc.parse.*`)다. 문법 규칙에서 바로 나오는 것 둘은 전용 메시지가 있다:
조건 괄호 누락(`if hp <= 0`, 옛 `if let` 도 여기 걸린다)과 필드 타입 누락(`public MaxHp = 10`, §3.2).
한국어 문구는 MSVC 한국어판의 모양(`')'이(가) 필요합니다.`)을 따랐다.

> **"두 번 훑는다"(§2) 와 다르다 - 빡대리 확인 대기(2026-09-17).** §2 는 "먼저 모든 파일의 타입 이름을 모으고 몸통을 읽는다" 를
> [확정] 으로 적었다. 그 이유는 `var` 가 없어 `float step = dt` 가 선언인지 알려면 타입 이름을 먼저 알아야 한다는 것이었다.
> 그런데 **스크립트 파일에서 모은 타입 이름으로는 엔진 타입(`Transform2D`·`Collision2D`)을 알 수 없다** - 그 이름은 엔진 리플렉션을
> 링크하는 타입체커 단계에서야 생긴다. 그래서 타입 이름으로 가르는 파서는 `Collision2D hit` 를 읽지 못한다. 모양으로 가르면 이
> 문제가 없고 파일 하나만으로 읽을 수 있어 편집기(`jbroc --lsp`)에도 맞다. **모든 파일의 타입 이름을 먼저 모으는 일은 여전히
> 필요하다** - 다른 파일의 타입을 `import` 없이 쓰므로 타입체커의 이름 해석이 한다. 바뀌는 것은 "파서가 그것을 기다린다" 뿐이다.
> §2 는 확인을 받은 뒤 고친다.

**검증.** `Tests/ScriptCompilerParserTests.cpp`.

- 선언 종류 다섯, 필드(어트리뷰트·접근자·`static`·`const`·`ref`·중첩 제네릭), 함수(본문 유무·반환 타입·접미사 셋·생성자),
  문맥 키워드와 C++ 키워드를 필드 이름으로 쓴 경우를 덤프로 비교한다.
- 엔진 타입(`Collision2D`)으로 시작하는 선언, `a < b` 비교와 `GetComponent<Transform2D>()` 가 갈리는지, **읽어 본 노드가 트리에
  남지 않는지**(노드 수 = 덤프 줄 수)를 본다.
- 연산자 우선순위, `if`/`else if`/`else`, `while`, `for` 의 세 모양, `switch`, 여러 줄로 나눈 호출과 `ref` 인자.
- 에러 15가지를 **종류와 줄·열까지** 본다. 한 문장의 에러는 하나만 나고 다음 문장의 에러는 다시 나는 것, 선언 밖의 쓰레기 뒤의
  선언이 읽히는 것도 본다.
- **문법 문서 §13 의 전체 예시를 문서에서 직접 읽어** 에러 없이 파싱되고 선언 다섯 개가 나오는지 본다. 예시가 몸통을 줄인 자리의
  `...` 줄만 뺀다. 문서가 바뀌면 이 테스트가 먼저 안다.
