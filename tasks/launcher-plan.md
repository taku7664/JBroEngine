# JBro Launcher — WinUI 3 런처 계획

> 2026-09-16 작성. **L0(에디터 인자 규약)까지 섰고, 런처 앱 자체는 아직 없다.**
> 확정 계약이 아니라 계획이므로 `docs/ProjectRule.md` 가 아니라 여기에 둔다.
> 인자 규약과 종료 코드는 확정 계약이라 [todo.md](./todo.md) D-97 과
> `docs/ProjectRule.md` §11.6 에 있고, 이 문서는 그 위에 세울 런처의 계획을 적는다.

---

## 0. 결론 먼저

- 제품 이름은 **JBro Launcher** 다. 유니티 허브가 하는 일(프로젝트 목록, 엔진 버전 관리,
  프로젝트를 골라 에디터 실행)을 맡는다.
- **C# / WinUI 3 로 만들고, 엔진과 같은 리포에 둔다.** 엔진 에디터와 항상 같이 배포하므로
  리포를 나눌 이유가 없다.
- **런처와 에디터는 프로세스 경계로만 만난다.** 런처가 `JBroEditorHost.exe` 를 인자와 함께
  실행하고, 종료 코드와 표준 출력으로 결과를 받는다. C++/CLI 나 P/Invoke 로 엔진을 안에
  싣지 않는다 — 엔진이 죽어도 런처는 살아 있어야 한다.
- **런처 전용 정보는 런처가 자기 파일에 보관한다.** `.jproject` 는 기존 엔진과 공유하는
  형식이므로(ProjectFile.h) 런처 편의를 위해 키를 더하지 않는다.
- **다중 엔진 버전을 전제로 만든다.** 프로젝트마다 어느 엔진 설치로 열지 기억한다.
- **비패키지로 배포하고 Windows App SDK 를 자체 포함한다**(2026-09-16 확인, §4 Q4).
- **스크립트 DLL 이 없는 프로젝트도 에디터가 연다**(D-98). 새 프로젝트 만들기가 여기에
  막혀 있었고, 지금은 열린 뒤 경고가 나온다.

## 1. 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| L0 | 에디터 실행 인자 규약과 종료 코드(D-97) | **완료** (2026-09-16) |
| L1 | 런처 앱 뼈대: WinUI 3 프로젝트, 프로젝트 목록 읽기·쓰기, 에디터 실행 | 미착수 |
| L2 | 엔진 설치 목록(다중 버전), 프로젝트마다 엔진 고르기 | 미착수 |
| L3 | 새 프로젝트 만들기(템플릿, 스크립트 첫 빌드) | 미착수 |

### L0 에서 실제로 한 것

- `JBroEditorHost` 의 `main` 이 인자를 해석한다. 예전에는 첫 인자를 프레임 수로 읽었고
  프로젝트를 열 길이 없었다.
- `EditorApplication::OpenProjectFile` 로 `.jproject` 를 열도록 배선했다. 프로젝트를 주지
  않으면 예전처럼 확인용 씬이 뜬다.
- `--content-root` 로 로컬라이징 표와 아이콘 글꼴의 기준 폴더를 밖에서 정할 수 있다.
  런처가 작업 폴더를 옮기지 않고도 엔진 리소스를 찾게 하는 자리다.
- 아이콘 글꼴을 ImGui 에 경로로 넘기지 않고 직접 읽어서 넘긴다. 설치 경로에 한글이 섞이면
  ImGui 가 파일을 못 열고 단언으로 죽던 것을 고쳤다(§3).

## 2. 런처가 실행하는 방법

```
JBroEditorHost.exe --project <프로젝트.jproject> --framework 2d --content-root <엔진 폴더>
```

- 종료 코드: `0` 정상, `1` 초기화 실패, `2` 프로젝트 열기 실패, `3` 에디터 UI 실패,
  `64` 인자 오류. 런처는 이 값으로 사용자에게 무엇이 틀어졌는지 구분해 보여 준다.
- 실패 사유는 표준 출력에도 한 줄로 나온다. 프로젝트 파일이 형식에 어긋나면 줄 번호가
  같이 나오므로(`ProjectFile.h`) 런처가 그대로 보여 주면 된다.
- `--framework` 는 런처가 정한다. `.jproject` 에는 2D 인지 3D 인지 적는 자리가 없다 —
  기존 엔진이 2D 전용이라 그 키가 없고, 여기서 키를 지어내면 그 쪽 프로젝트를 열 때
  무엇을 적어야 할지 모르게 된다.

## 3. 경로 인코딩 — 확인한 것

한국어 윈도우에서 콘솔 실행 파일의 `argv` 는 UTF-8 이 아니라 이 기계의 ANSI 코드페이지
(949)로 들어온다. 엔진이 경로를 C 런타임(`fopen_s`)으로 열 때는 이것이 맞아떨어져서
한글이 섞인 프로젝트 경로도 열린다. **어긋나는 곳은 ImGui 다** — ImGui 는 받은 경로를
UTF-8 로 보고 넓은 문자로 바꾸므로, 한글이 섞인 경로를 주면 파일을 못 열고 단언으로
죽는다. 실제로 `--content-root` 에 `C:\Users\박주형\...` 를 주자 에디터가 거기서 죽었다.

L0 에서는 아이콘 글꼴을 직접 읽어 메모리로 넘기는 방식으로 이 한 곳을 막았다. 남은
위험은 **ImGui 에 경로를 넘기는 다른 자리**이고, 지금은 없다. 새로 만들 때 주의한다.

## 4. 남은 질문

- **Q1. 스크립트 DLL 이 없는 프로젝트를 열 수 있어야 하는가.** **→ 닫혔다(D-98).**
  엔진이 열고 경고만 남긴다. `IsScriptModuleLoaded()` 가 false 이고
  `GetScriptModuleError()` 에 사유가 들어 있으며, 호스트가 `warning:` 한 줄을 낸다.
  런처는 이 줄을 그대로 보여 주면 된다. 에디터 화면에 띄우는 것은 L1 에서 한다.
- **Q2. 엔진 설치 폴더의 모양을 무엇으로 정할 것인가.** `[열림]`
  지금은 `Localization/` 과 `ThirdParty/` 가 실행 파일 옆으로 복사되지 않아서,
  에디터를 리포의 `source/JBroEngine` 을 작업 폴더로 두고 실행해야 글자와 아이콘이 나온다.
  배포본에서는 실행 파일과 리소스가 한 폴더에 있어야 하고, 그 모양이 정해져야 런처가
  엔진 설치를 등록할 수 있다.
- **Q3. 프로젝트가 어느 엔진 버전으로 열리는지 어디에 적을 것인가.** `[열림]`
  `.jproject` 에는 엔진 버전 키가 없다. 런처 목록에만 두면 프로젝트 폴더를 다른 기계로
  옮겼을 때 그 정보가 따라가지 않는다. 반대로 `.jproject` 에 키를 더하면 기존 엔진이
  모르는 키를 만나는데, 그 쪽은 모르는 키를 건너뛰므로 깨지지는 않는다(ProjectFile.h).
- **Q4. 배포 형태를 MSIX 로 묶을 것인가, 비패키지로 둘 것인가.** **→ 닫혔다(2026-09-16 확인).**
  **비패키지로 두고 Windows App SDK 를 자체 포함한다**(`WindowsAppSDKSelfContained`).
  임의 경로의 프로젝트를 다루는 도구라 비패키지가 편하고, 자체 포함이면 사용자가 런타임을
  따로 깔지 않는다. 대신 배포 용량이 늘어난다.
