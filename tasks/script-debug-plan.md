# 에디터 안의 스크립트 디버깅 (D-330)

> 2026-10-14 작성. 스크립트 중단점에 걸려도 에디터가 멈추지 않고, 스크립트가 죽어도 에디터가 살게 하는 계획이다.
> 시뮬레이션은 지금처럼 에디터 프로세스에서 돌고, 중단점과 스크립트 예외를 엔진이 직접 받는다.
> 시뮬레이션을 다른 프로세스로 옮기는 계획(D-320)을 대체한다.

## 1. 왜 같은 프로세스인가

- 에디터가 멈추는 원인은 중단점이 아니라 **OS 디버거가 붙어 있다는 것**이다. 디버거가 붙은 프로세스에서 중단점이 걸리면 Windows 가 그 프로세스의 스레드를 전부 세운다.
  같은 프로세스의 다른 스레드로 시뮬레이션을 옮겨도 똑같이 선다.
- D-320 은 시뮬레이션을 다른 프로세스로 옮겼다. 그러면 에디터의 하이어라키·인스펙터·캔버스 뷰가 실행 중 상태를 보이려고 **매 프레임 오브젝트 상태를 복사**해야 한다.
  캔버스 뷰만 해도 `CanvasViewPanel.cpp` 가 모든 오브젝트를 돌며 마커·콜라이더·조인트·카메라 영역을 그린다(`DrawObjectMarkers`·`DrawColliders`·`DrawJoints`·`DrawCameraAreas`).
  사용자가 이 비용을 받아들일 수 없다고 했다.
- 그래서 OS 디버거로 붙지 않는다. 엔진이 스크립트 DLL 에 int 3 을 직접 넣고, 걸리면 예외 처리기(VEH)가 받아 **그 자리에서 에디터 화면만 그리는 루프**를 돌린다.
  디버그 어댑터는 프로세스를 세우지 않는 붙기(noninvasive, no-suspend)로 메모리만 읽는다.
- 스크립트가 던진 예외(잘못된 포인터 등)도 엔진이 받는다. 실행을 멈추고 실행 전 캔버스로 되돌린다.

## 2. 실측 (2026-10-14, 임시 시험 코드, 커밋하지 않았다)

### 2.1 멈추지 않고 붙어서 읽기

스크래치 호스트(에디터 역할)가 `JBroDebugAdapterTargetScript.dll` 을 50 ms 마다 부르고, 별도 프로그램이 재배포용 DbgEng(10.0.29547)으로 붙었다.

| 확인한 것 | 결과 |
|---|---|
| `AttachProcess(DEBUG_ATTACH_NONINVASIVE \| DEBUG_ATTACH_NONINVASIVE_NO_SUSPEND)` | 붙었다. 붙은 동안 호스트 루프가 계속 돌았다(heartbeat 22 → 27, 300 ms) |
| 소스 줄 → 주소 | `GetOffsetByLine` 이 됐다. 먼저 그 모듈의 심볼을 읽어야 한다(`x <모듈>!<함수>` 뒤에 됐고 `ld` 는 "No modules matched") |
| int 3 넣기 | `WriteVirtual` 로 넣고 원래 바이트를 되돌렸다 |
| 멈춘 자리 읽기 | 호스트의 VEH 가 넘긴 `CONTEXT` 주소로 `.cxr` 을 하면 `k` 가 스크립트 줄(`TargetScript.cpp @ 20`)부터 나오고, `GetStackTrace` 도 그 프레임부터 5 개를 냈다 |
| natvis 값 | `.nvload JBro.natvis` 뒤 `dv /t`·`dx` 가 `Float 2.5`·`Vector2 (1, 2)`·`Array { size=3 }` 과 원소·`String "hello"` 를 보였다 |
| 멈춘 동안 호스트 | VEH 안의 루프가 계속 돌았다(heartbeat 37 → 70, 500 ms) |
| 재개 | 원래 바이트로 되돌리고 플래그를 쓰자 호스트가 같은 자리(`Rip` = int 3 주소)에서 이어 돌았다 |
| 안 된 것 | 데이터 모델의 `@$curthread.Stack.Frames[0].LocalVariables` 는 `.cxr` 을 따르지 않아 비었다. 어댑터의 스택·변수 경로를 `.cxr` 기준으로 바꿔야 한다 |

### 2.2 실제 에디터에서 중단점 루프와 스크립트 예외

워크트리 에디터에 임시 코드를 넣었다. `ScriptSystem` 의 `OnUpdate` 호출을 SEH 로 감싸고, VEH 가 `EXCEPTION_BREAKPOINT` 를 받으면 8 초 동안 에디터 UI 와 그리기만 하는 루프를 돌린다
(엔진 쪽은 프레임워크 갱신 없이 `Render`·`RenderEditorView` 만). 스크립트는 120 번째 `OnUpdate` 에서 `__debugbreak()`, 300 번째에서 null 에 쓴다.

| 확인한 것 | 결과 |
|---|---|
| 중단점에서 에디터 | 8 초 동안 1921 프레임을 그렸다. 창이 응답했다(`SendMessageTimeout` 성공, `IsHungAppWindow` 거짓) |
| 멈춘 동안 조작 | 캔버스 뷰 탭과 오브젝트를 눌렀다. 캔버스 뷰가 스크립트가 옮긴 위치 (3, 1) 를 기즈모와 함께 그렸고, 인스펙터가 `Transform2D`·`NewScript`·`follow` 를 보였다 |
| 재개 | 루프가 끝나자 시뮬레이션이 이어 돌았다 |
| 스크립트 예외 | `0xc0000005` 를 받아 실행을 멈추고 캔버스를 되돌렸다. 에디터는 살아 있고 응답했다 |

재지 않은 것: 실제 에디터에 noninvasive 로 붙어 읽기(2.1 은 스크래치 호스트), 멈춘 동안 게임 카메라가 있는 시뮬레이션 뷰, 오디오, D3D11·Vulkan 백엔드, 3D.

## 3. 설계

### 3.1 중단점과 한 줄 가기

- 엔진이 중단점 표(주소·원래 바이트)를 들고 스스로 int 3 을 넣고 뺀다. 어댑터는 소스 줄을 주소로 바꿔 엔진에 넘긴다. 스크립트 DLL 을 다시 실으면 어댑터가 새 주소를 다시 넘긴다.
- VEH 는 표에 있는 주소의 `EXCEPTION_BREAKPOINT` 와 엔진이 건 한 걸음(`EXCEPTION_SINGLE_STEP`)만 받는다. 나머지는 그대로 넘긴다.
- 재개: 원래 바이트로 되돌리고 트랩 플래그로 한 명령만 가서 int 3 을 다시 넣는다.
- 한 줄 가기·들어가기·나가기: 트랩 플래그와 줄 정보로 한다. 나가기는 돌아갈 주소에 임시 int 3 을 둔다. 줄을 판단하는 쪽(엔진 또는 어댑터)은 미정.
- 미정: 엔진과 어댑터 사이 통로. 에디터의 제어 포트(D-270, 루프백)를 넓힐지 이름 있는 파이프를 둘지.

### 3.2 멈춘 동안의 에디터

- VEH 안에서 에디터 루프를 돈다. 에디터 UI 를 만들고, 엔진은 프레임워크 갱신 없이 게임 화면·캔버스 뷰만 그린다.
- 멈춘 동안 **보기·고르기·카메라 이동은 되고 캔버스 편집은 막는다.** 스크립트 스택이 쥔 오브젝트를 지우면 재개할 때 죽는다.
- 멈춘 동안 정지를 누르면: 재개하면서 스크립트 자리를 엔진의 예외로 돌려 3.3 의 보호가 받게 하고, 그다음 지금의 정지(되돌리기)를 한다. `[제안]`
- 미정: VEH 안에서 루프를 돌릴지, VEH 는 `Rip` 만 돌려 놓고 보통 함수에서 돌릴지. 실측은 VEH 안에서 했다.
- 미정: 멈춘 동안 프레임 메모리(`m_frameMemory`)를 되감지 않는다 - 바깥 프레임이 쓰던 것이다. 오래 서 있을 때 모자라는지 재지 않았다. 오디오 믹서는 멈춰야 한다.

### 3.3 스크립트 예외에서 에디터 살리기

- 스크립트 훅을 부르는 모든 자리를 SEH 로 감싼다. `ScriptSystem` 의 `OnCreate`·`OnStart`·`OnUpdate`·`OnFixedUpdate`·`OnDestroy` 뿐 아니라 물리 충돌 콜백(`Physics2DSystem`)·버튼 콜백처럼
  엔진이 스크립트를 부르는 자리를 전부 찾아 감싼다(아직 목록을 만들지 않았다).
- 받으면 그 프레임의 스크립트 호출을 멈추고, 에디터가 실행을 멈춰 실행 전 캔버스로 되돌린다. 오류 코드와 스크립트 파일·줄을 알린다.
- 막는 것과 못 막는 것:

| 스크립트가 죽는 방식 | 에디터 |
|---|---|
| 잘못된 포인터·0 으로 나누기 | 산다(실측: null 쓰기) |
| 스택 넘침 | 산다 - `_resetstkoflw` 처리가 더 필요하다(재지 않았다) |
| 스크립트가 던진 C++ 예외 | 산다(재지 않았다). 스크립트 프레임의 소멸자는 돌지 않지만 캔버스를 버리므로 괜찮다 |
| 무한 루프 | 멈춘다. 감시 스레드로 끊는 것은 나중 일이다 |
| 엔진 메모리를 덮어쓴 뒤 | 그 순간은 넘겨도 뒤에 죽을 수 있다 |
| `__fastfail`(버퍼 넘침 검사·CRT 힙 손상)·`abort` | 못 막는다. 프로세스가 바로 끝난다 |

### 3.4 그냥 실행과 디버그 실행

- 3.3 의 보호는 둘 다 켠다.
- 디버그 실행은 어댑터가 붙고 중단점을 넣은 뒤 첫 프레임을 돌린다.
- 미정: 디버그 실행이 아닐 때 스크립트의 `__debugbreak()` 를 멈춤으로 볼지 무시할지.

### 3.5 어댑터(D-319)에서 바뀌는 것

- OS 디버거 붙기(`AttachProcess` 기본) → noninvasive no-suspend 붙기. 디버그 이벤트를 받지 않으므로 멈춤·재개·모듈 실림 알림은 엔진이 통로로 보낸다.
- 스택과 변수는 엔진이 알려 준 `CONTEXT` 주소로 `.cxr` 한 뒤 읽는다. 데이터 모델의 `@$curthread` 경로는 쓰지 못한다(2.1).
- 중단점은 어댑터가 넣지 않고 주소만 넘긴다.

### 3.6 정할 것과 추천 (2026-10-15 정리)

위 절의 `미정` 을 한곳에 모은다. 2 단계(중단점 루프) 앞에 정한다. 멈춘 동안 오디오는 선다(3.2).
2026-10-15 사용자가 일곱 줄 모두 추천대로 정했다(아래 `정함`). 통로는 파이프가 에디터와 어댑터 사이일 뿐 시뮬레이션을 프로세스로 빼는 것이 아니라는 설명을 듣고 정했다 - 실행은 지금처럼 에디터 프로세스 안에서 돈다.

### 4.1 스크립트 예외 보호 (1 단계)

- `JBroRuntime` 의 `ScriptCallGuard`(`ScriptCallGuard.h`): `Call(hook, callable)` 이 SEH 로 감싼다. 켜져 있지 않으면(게임) 그냥 부른다. 첫 예외의 코드·주소·훅·스택(32 칸)을 적고, 꺼낼 때까지 다음 훅은 부르지 않는다.
  스택 넘침은 스택을 읽지 않고 받은 뒤 `_resetstkoflw` 로 지킴 페이지를 되살린다. 상태는 링크한 바이너리마다 있어 스크립트 DLL 의 사본은 꺼진 채다.
- 감싼 자리(전수, 2026-10-15 `grep` 으로 엔진이 스크립트 훅을 부르는 자리를 모두 찾았다): `ScriptSystem` 의 `OnCreate`·`OnStart`·`OnUpdate`·`OnFixedUpdate`·`OnDestroy`,
  `Physics2DSystem` 의 충돌·트리거 여섯, `Button2DSystem` 의 포인터·클릭 다섯, `Canvas` 의 `OnAttached`·`OnDetached`, `GameScriptBase::SetEnabled` 의 `OnEnabled`·`OnDisabled`. 3D 에는 스크립트 훅을 부르는 자리가 없다.
  감싸지 않은 것: 스크립트의 생성자·소멸자(스크립트 풀이 만들고 지울 때), DLL 을 실을 때의 정적 초기화.
- 플랫폼(`IPlatform`): `CaptureFaultFrames` 가 예외 자리부터 함수 표로 거슬러 올라가고(`RtlVirtualUnwind`, 필터 안이라 할당·잠금 없음), `DescribeCodeAddress` 가 dbghelp 로 모듈·함수·파일·줄을 준다. Windows 만 구현했다.
- 에디터: `Initialize` 에서 켜고 `ReleaseProcessResources` 에서 끈다. `PollScriptFault` 가 프레임 앞에서 꺼내, 스택을 로그에 적고, 실행 중이면 `StopSimulation`, 오류 알림(`notify.script_fault_stopped`·`notify.script_fault`)을 띄운다.
  알릴 줄은 스택에서 처음 나오는 스크립트 DLL 프레임이다. 스크립트 DLL 은 세대마다 다른 이름의 사본이라, 진입점(`JBroScriptModule_GetApi`)이 든 모듈의 경로와 맞춘다. 알림을 누르면 그 줄을 연다(`OpenInScriptEditor`).
- 시험: `ScriptCallGuard` 묶음(꺼짐·null 쓰기의 코드와 파일·줄·호출한 쪽까지의 스택·예외 뒤 막힘·스택 넘침 두 번·C++ 예외), `ScriptFault` 묶음(적대적 시나리오, 아래), `EditorApplication` 의 `TestAScriptFaultStopsPlayAndTellsTheUser`.
- **적대적 시나리오**(`ScriptFault`): 시험이 등록한 스크립트를 에디터의 진짜 `ScriptSystem`·물리 경로로 돌려 터트린다. `OnCreate` 의 null 쓰기, `OnStart` 의 C++ 예외, `OnUpdate` 의 null 쓰기·정수 0 나누기·끝없는 재귀·`__debugbreak`,
  `OnFixedUpdate` 의 null 쓰기, `OnCollisionEnter` 의 null 쓰기, 오브젝트 20 개를 만들고 남의 오브젝트를 지우고 값을 옮긴 뒤의 null 쓰기, 스크립트가 붙은 오브젝트를 지운 뒤의 null 쓰기, 일시정지에서 한 프레임 진행으로 들어간 null 쓰기.
  시나리오마다 실행이 멈추고, 예외가 꼭 하나만 나고(같은 프레임의 둘째 스크립트 훅이 불리지 않는다), 에디터 프레임이 계속 돌고, **캔버스 글자가 실행 전과 똑같고**, 오류 알림과 예외 코드 로그가 남고, 다음 실행에서 훅이 다시 돈다. 같은 에디터에서 두 바퀴 돌린다.
  편집 중 `OnAttached` 의 null 쓰기는 멈출 것 없이 알리기만 하고 캔버스를 그대로 둔다. 2026-10-15 22 시나리오와 편집 중 하나가 모두 지났다(2.3 초).
- 뮤테이션 셋 모두 잡혔다: 실행을 멈추지 않게 하면 "the fault must stop the simulation", 예외 뒤 훅을 막지 않으면 "a hook after a fault is refused", `_resetstkoflw` 를 빼면 두 번째 스택 넘침에서 시험 프로세스가 죽는다.
- 실제 에디터(워크트리 Debug, 2026-10-15): 실제 스크립트 DLL 이 120 번째 `OnUpdate` 에서 null 에 쓰자 실행이 멈추고 캔버스가 돌아왔으며, 알림이 `잘못된 메모리에 접근했습니다 - NewScript.cpp:20 (OnUpdate)` 로 그 줄을 가리켰다.
  끝없는 재귀는 `스택이 넘쳤습니다 ... NewScript.cpp:6` 으로 재귀 함수를 가리켰다. 알림을 눌러 편집기가 열리는 것은 재지 않았다.
- 찾은 것(이 단계와 무관, 고치지 않았다): `OnDestroy` 는 시스템이 내려갈 때(`ScriptSystem::OnShutdown`)만 불린다. 실행 중에 오브젝트를 지울 때도, 정지할 때도 불리지 않는다.
  최소화 상태(`-WindowStyle Minimized`)로 띄운 에디터가 `the editor could not initialize` 로 끝난다 - 원인은 보지 않았다.

### 4.2 중단점 루프 (2 단계)

- 플랫폼(`IPlatform`): `SetCodeBreakHandler` 가 벡터 예외 처리기(VEH)를 맨 앞에 걸고, `SetCodeBreakpoint`·`ClearCodeBreakpoint` 가 코드에 int 3 을 넣고 뺀다(표 256 칸, 원래 바이트를 든다). Windows 만 구현했다(`WindowsCodeBreak.cpp`).
  처리기를 건 스레드의 int 3 만 받는다. 표에 있는 자리면 넣은 중단점, 표에 없는데 그 바이트가 int 3 이면 코드에 든 것(`__debugbreak`)이다. 처리기가 돌려준 값대로
  `Continue`(넣은 것은 원래 바이트로 되돌리고 트랩 플래그로 한 명령 간 뒤 다시 넣는다, 코드에 든 것은 건너뛴다)·`Stop`(예외로 나아가게 둔다)·`Pass` 를 한다.
- 런타임: `ScriptCallGuard::IsInCall` - 감싼 훅 안인지다. 스크립트가 도는 동안의 멈춤만 받는다.
- 엔진(`EngineInstance`): `BeginBreakFrames`·`RenderBreakFrame`·`EndBreakFrames`. `TickFrame` 의 그리기 쪽을 `RenderFrame` 으로 떼어 선 동안의 프레임이 같은 길을 돈다.
  선 동안에는 `Tick` 안이어도 시뮬레이션 뷰·편집 화면·썸네일 요청을 받는다. 오디오 믹서는 `AudioMixer::SetFrozen` 으로 선다 - 장치에 0 을 내고 한 표본도 나아가지 않아 풀면 그 자리에서 이어진다.
  프레임 메모리는 `LinearAllocator::Mark`·`RewindTo` 로 선 자리를 표시하고 안쪽 프레임마다 거기로 되감는다.
- 프레임워크(`IFramework::PrepareBreakFrames`·`EndBreakFrames`): **선 자리는 이번 프레임의 추출 전이다** - 갱신 첫머리에서 렌더 목록을 비우고 추출은 스크립트 뒤에 돈다.
  그대로 그리면 시뮬레이션 뷰가 `카메라가 없습니다` 였다(화면으로 봤다). 그래서 설 때 트랜스폼·카메라·스프라이트·라이트·그림자·텍스트 시스템만 지금 캔버스로 한 번 돌려 목록을 채우고,
  끝날 때 비워 이어지는 갱신의 추출이 처음부터 채운다. 시스템 스케줄러는 다시 들어갈 수 없어(`ExecutionScope` 가 던진다) 시스템을 직접 부른다.
- 에디터: `Initialize` 에서 처리기를 건다. 재생 중이고 감싼 훅 안이며 UI 가 켜져 있을 때만 선다 - 아니면 `Pass`(편집 중 `OnAttached` 의 `__debugbreak` 는 지금처럼 스크립트 예외, 넣은 중단점은 그냥 지나간다).
  선 동안 그 자리에서 `BuildEditorUi` → 프레임 요청 → `RenderBreakFrame` 을 돈다. 커맨드는 잠기고(`EditorCommandManager::SetLocked`) 인스펙터의 값 칸·머리·`컴포넌트 추가` 가 흐리게 잠긴다(펼치기는 된다).
  `IsSimulationPaused` 는 참이라 도구 모음의 일시정지 풀기가 이어 가기, 재생 단추·`StopSimulation` 이 정지다. 한 프레임 진행은 막는다(`blocked.at_script_break`).
  정지는 그 훅을 예외로 끝내고, 다음 프레임의 `PollScriptFault` 가 오류 알림 없이 실행을 멈춘다. 창을 닫거나 끝내기를 골라도 먼저 정지한다.
  알림(`notify.script_break`)은 파일·줄·함수를 말하고 선 동안 떠 있으며 누르면 그 줄을 연다. 시뮬레이션 뷰의 상태 줄이 `중단점 PlayerMover.cpp:19 에서 멈춤` 이다.
  스크립트 DLL 을 다시 싣기 전에 넣은 중단점을 모두 뺀다. 디버그 어댑터가 쓸 자리는 `SetScriptBreakpoint`·`ClearScriptBreakpoint` 다(3 단계에서 통로에 잇는다).
- §3.6 의 (다)가 섰다: 디버그 실행이 아니어도 스크립트의 `__debugbreak()` 는 중단점처럼 선다. 그래서 `ScriptFault` 의 `__debugbreak` 시나리오는 `ScriptBreak` 로 옮겼다.
- 시험: `ScriptBreak` 묶음 - `__debugbreak` 에서 서서 둘러보고(선 자리의 파일·줄·함수, 선 동안 그린 프레임, 막힌 편집과 한 프레임 진행) 일시정지를 풀면 이어 돎,
  선 자리에서 정지하면 그 뒤 훅이 하나도 돌지 않고 오류 알림 없이 캔버스가 돌아옴, 넣은 중단점이 세 프레임 연달아 걸리고 빼면 원래 코드가 매 프레임 돎, 실행 밖에서 걸린 넣은 중단점이 그냥 지나감.
  `FrameMemory` 의 `TestMarkKeepsTheOuterFrame`. 사용자 시나리오 A 의 13 단계(실제 MSBuild 로 빌드한 `PlayerMover.cpp` 의 `__debugbreak`, 화면 `a16`·`a16b`·`a17`).
- 뮤테이션 둘 다 잡혔다: 한 명령 뒤 int 3 을 다시 넣지 않으면 "the breakpoint caught the first three frames", 커맨드를 잠그지 않으면 "editing is refused while the script stands".
- 스택(§3.6 에서 재기로 한 것): `ScriptBreak` 의 첫 시나리오 뒤 이 스레드의 커밋된 스택이 1024 KB 중 124 KB 였다(Debug, 그때까지 가장 깊이 쓴 양). 시험이 절반을 넘지 않는지 본다.
- 전체 시험(2026-10-15): 한 번 `EditorApplication` 의 긴 글자 칸 시험이 1 바이트로 돌아와 실패했다 - 숨긴 창에 키 메시지를 넣는 시험이고 단독으로 다시 돌리자 1501 바이트로 지났다. 이번 변경과 닿지 않는 흔들림으로 본다(추측, 원인은 보지 않았다). 그 뒤 묶음도 모두 지났다.
- 재지 않은 것: 실제 `JBroEditorHost` 창에서 사람이 누르는 것(시험은 같은 에디터를 숨긴 창으로 돌렸다), 물리 충돌 콜백·`OnFixedUpdate` 에서 서기, D3D11·Vulkan, 선 동안 프로젝트 열기 같은 메뉴(요청은 이어 간 뒤의 프레임이 처리한다).
- 남은 것: 선 동안 게임 카메라를 바꾸는 시뮬레이션 뷰 조작은 지난 추출을 그린다. 넣은 중단점은 처리기를 건 스레드에서만 받는다 - 스크립트가 워커에서 돌 일이 생기면 다시 본다.

### 4.3 어댑터 연결 (3 단계)

- 플랫폼: `IPlatform::OpenLocalPipe` 가 지금 사용자만 닿는 이름 있는 파이프를 연다(겹치기, 막히지 않음, 원격 거부). `WindowsLocalPipe.cpp`. `PlatformContract` 가 두 쪽 왕복과 끊김을 본다.
- 에디터: `ScriptDebugServer` 가 `jbro-debug-<pid>` 를 열고 통로와 중단점·멈춤 API 를 잇는다. 어댑터가 `setbp`·`clearbp`·`continue`·`stop` 을 보내면, 에디터가 `bp`(setbp 답)·`stopped <주소> <문맥주소> <스레드>`·`resumed`·`module`·`exited` 를 보낸다. `Poll` 은 프레임마다, 그리고 멈춤 루프 안에서 돈다 - 멈춘 동안 어댑터가 이어 가게 할 수 있다. 멈춘 스레드 번호는 `CodeBreak` 에 실린다.
- 어댑터(`source/JBroDebugAdapter`): **세우지 않고 붙는다**(`DEBUG_ATTACH_NONINVASIVE | ..._NO_SUSPEND`) - 메모리와 심볼만 읽고 에디터는 멈추지 않는다. 디버그 이벤트가 오지 않으므로 멈춤·재개·모듈은 통로로 받는다. 중단점은 줄을 주소로 바꿔(`EvaluateWide` `` `모듈!파일:줄` ``) `setbp` 로 넘기고, `stopped` 를 받으면 `.cxr <문맥주소>` 한 뒤 스택·변수를 그 문맥으로 읽는다. 데이터 모델의 `@$curthread` 는 `.cxr` 을 따르지 않아 scope 는 `@$curframe.LocalVariables` 로 읽는다. DbgEng 이벤트 콜백(`SessionEvents`)은 버렸다.
- 시험(`DebugAdapter`): 대상 프로그램을 **에디터 흉내**로 다시 썼다(`Tests/DebugAdapterTarget`) - 통로를 열고, `setbp` 에 `bp` 로 답하고, 스크립트가 BREAK_HERE 에서 자기 문맥을 떠 `stopped` 를 보내고 `continue` 를 기다린다. 어댑터가 세우지 않고 붙는 동안 대상이 계속 돌고, 줄 → 주소 + `setbp` 로 중단점이 서고, `stopped` 뒤 `.cxr` 로 읽은 스택에 스크립트 파일이 보이고, 스크립트 프레임의 지역 변수가 natvis 값(`Float 2.5`·`String hello`·`Array size=3`)으로 나오고, 이어 가고, 떼어도 대상이 사는 것을 본다.
- 재지 않은 것: 실제 에디터(+엔진 int 3)와 어댑터를 함께 붙여 돌리기(시험은 대상이 문맥을 직접 뜬다), 다시 실은 복사본에서의 중단점 재배치(에디터의 `module` 알림 경로), Release 구성.

### 4.4 한 줄 가기 (4 단계)

- 플랫폼: `IPlatform::RequestCodeStep(kind)` 를 중단점 처리기 안에서(돌려주기 전에) 부르면, VEH 가 돌아간 뒤 트랩 플래그로 소스 줄이 바뀔 때까지 간다(`WindowsCodeBreak.cpp`).
  명령마다 dbghelp 로 줄을 읽어 시작 줄과 비교한다. 넘어가기(Over)는 스택이 더 깊으면(부른 함수 안) 멈추지 않고 지나고, 들어가기(Into)는 줄이 바뀌면 멈추며, 나가기(Out)는 스택이 얕아지면(돌아감) 멈춘다. 줄이 바뀌면 처리기를 그 자리에서 다시 부른다 - 에디터가 새 `stopped` 를 보낸다. 2백만 명령을 넘으면 폭주를 막으려 선다.
- 에디터: 멈춤 루프의 요청에 `Step` 을 더했다. 어댑터가 `step over|into|out` 을 보내면 서버가 `EditorApplication::StepScriptBreak(kind)` 를 부르고, `HandleCodeBreak` 가 `RequestCodeStep` 뒤 `Continue` 를 돌려준다.
- 어댑터: `next`·`stepIn`·`stepOut` 을 `step over|into|out` 으로 통로에 넘긴다(`OnResume`). "다음 줄" 은 엔진이 판단한다(§3.6).
- 시험: `ScriptBreak` 의 `TestSteppingAdvancesTheLine` - `__debugbreak` 에서 서서 넘어가기를 두 번 하면 멈춤 줄이 매번 뒤로 간다. 뮤테이션으로 확인: 한 줄 가기 신청을 무시하면 다시 서지 않아 "stopped at the break and after two steps" 가 실패한다.
- 남은 것: 한 줄 가기 중 정지(`stop`)는 그 자리에 int 3 이 없어 예외로 세우지 못한다 - 이어 가되 다음 보호 경계에서 선다.

## 5. 대체한 계획

D-320(시뮬레이션 프로세스)은 이 계획으로 대체했다. 남긴 생각: 같은 프로세스로는 `__fastfail`·`abort`·메모리 덮어쓰기를 막지 못한다. 이것까지 막아야 하면 프로세스 분리밖에 없다.
