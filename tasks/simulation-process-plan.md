# 시뮬레이션 프로세스 (D-320)

> 2026-10-14 작성. 에디터의 실행(재생)을 에디터 밖의 **시뮬레이션 프로세스**로 옮기는 계획이다.
> 스크립트 중단점에 걸려도 에디터가 서지 않게 하는 것이 목적이고, 사용자가 보는 실행 동작은 지금과 같게 둔다.
> 그냥 실행과 디버그 실행이 같은 길을 쓴다.

## 1. 왜 프로세스인가

- 지금은 에디터 메인 스레드가 `ScriptSystem::OnUpdate` 로 스크립트를 돌린다. DbgEng 같은 OS 디버거가 중단점에서 서면 Windows 가 **그 프로세스의 모든 스레드**를 세우므로
  에디터 화면까지 멈춘다(`WaitForDebugEvent` 의 동작, D-319 실측에서도 에디터 전체가 섰다).
- 시뮬레이션을 같은 프로세스의 다른 스레드로 옮겨도 OS 디버거 아래에서는 똑같이 선다. 스레드로 가려면 디버거를 직접 만들어야 한다
  (엔진이 int 3 을 넣고 VEH 로 받아 그 스레드만 재우기, 한 줄 가기·변수 읽기도 직접). 그래서 프로세스를 고른다.
- 스크립트만 밖에 두는 길은 없다. 스크립트는 프레임마다 컴포넌트를 찾고 트랜스폼을 읽고 쓰며, 그 호출을 하나씩 프로세스 사이로 보내면 프레임이 버티지 못한다.
  **시뮬레이션 라이프 사이클 전체**(캔버스 사본·시간·물리·스크립트 훅·입력·오디오·게임 화면 그리기)를 시뮬레이션 프로세스가 든다.

## 2. 사용자에게 그대로인 것

| 항목 | 지금 | 시뮬레이션 프로세스 뒤 |
|---|---|---|
| 실행 중 하이어라키·인스펙터·캔버스 뷰 | 도는 캔버스를 보이고 고칠 수 있다 | 같다. 에디터는 시뮬레이션 프로세스가 보낸 상태를 자기 캔버스에 비춘다 |
| 정지 | 실행 전 상태로 되돌린다 | 같다. 실행 전에 뜬 캔버스 글자를 다시 읽는다 |
| 일시정지·한 프레임 진행 | 있다 | 같다. 명령으로 보낸다 |
| 게임 화면 | ImGui 시뮬레이션 뷰 | 사용자 설정으로 별도 창(기본) 또는 ImGui 시뮬레이션 뷰 |
| 스크립트 중단점 | 에디터 전체가 선다 | 시뮬레이션 프로세스만 선다. 에디터는 마지막으로 받은 상태를 보이며 돈다 |
| 스크립트가 죽음 | 에디터가 같이 죽는다 | 시뮬레이션 프로세스만 죽는다 |

달라지는 것(재지 않은 예상): 인스펙터의 값이 한 프레임 늦게 보이고 고친 값은 다음 프레임에 들어간다. ImGui 모드의 화면과 입력은 한 프레임쯤 늦을 수 있다.
실행을 누를 때 프로세스를 띄우고 에셋을 읽는 시간이 붙고, GPU 메모리를 두 벌 쓴다.

## 3. 구조

### 3.1 프로세스와 실행 파일

- `[제안]` 새 실행 파일 모듈 `JBroSimulationHost`. 에디터 구성(2D·3D 둘 다)으로 빌드하고 에디터 실행 파일 옆에 둔다.
  `JBroGameHost` 를 쓰지 않는 까닭: 게임 호스트는 `Debug_Game2D` 같은 차원별 구성으로만 빌드되어(`JBroGameHost.vcxproj`), 두 차원을 다 든 에디터의 런타임과 같지 않다.
- 에디터가 실행을 누르면 시뮬레이션 프로세스를 자식으로 띄우고, 실행 전에 뜬 캔버스 글자·프로젝트·스크립트 DLL·게임 언어·표시 방식을 넘긴다.
  정지는 명령으로 끝내고, 답이 없으면(중단점에 서 있으면) 프로세스를 끝낸다.
- 미정: 실행마다 띄울지, 하나를 띄워 두고 재사용할지. 1 단계의 시작 시간 실측으로 정한다.

### 3.2 통로

- `[제안]` 명령과 사건은 이름 있는 파이프, 프레임 상태는 공유 메모리 링 버퍼. 둘 다 같은 기계 안이라 소켓은 쓰지 않는다.
- 에디터 → 시뮬레이션: 실행·정지·일시정지·한 프레임·값 고치기(인스펙터 커맨드)·오브젝트 만들기와 지우기·스크립트 다시 싣기.
- 시뮬레이션 → 에디터: 프레임 상태(아래 미러), 로그, 끝남.

### 3.3 미러 - 가장 큰 미지수

- 시뮬레이션 프로세스가 원본이다. 에디터는 자기 캔버스에서 시뮬레이션을 돌리지 않고, 받은 상태를 반영만 한다. 하이어라키·인스펙터·캔버스 뷰는 지금처럼 그 캔버스를 본다.
- 프레임마다 오브젝트 생성·삭제와 바뀐 컴포넌트·스크립트 필드 값을 보낸다. 리플렉션(`PropertyInfo`)으로 모든 필드를 바이너리로 찍는 것이 후보다.
- 네트워크 복제(D-122, `CanvasPoolAdapter`)는 그대로 쓰지 못한다. 컴포넌트 타입마다 `Traits::Pack`/`Unpack` 을 손으로 두는 게임용 설계라 스크립트 필드와 모든 컴포넌트를 덮지 않는다.
  스냅숏을 풀 단위로 비교하는 생각만 가져온다.
- 캔버스 파일은 지금 글자(YAML)뿐이다(`CanvasFile.h`). 바이너리 직렬화는 새로 만든다.
- 미정: 오브젝트 번호(`InstanceId`)를 두 프로세스가 같게 쓸 수 있는지. 같으면 에디터의 선택과 커맨드 대상이 실행 중에도 그대로다. `ReadCanvasText` 가 번호를 지키는지 확인하지 않았다.

### 3.4 화면과 입력

- 별도 창(기본): 시뮬레이션 프로세스가 자기 창에 그리고 입력도 그 창이 받는다.
- ImGui 시뮬레이션 뷰: 시뮬레이션 프로세스가 공유 텍스처에 그리고 에디터가 그 텍스처를 시뮬레이션 뷰에 보인다. 입력은 에디터가 넘긴다(지금의 시뮬레이션 뷰 포커스 게이트 자리).
  미정: D3D11·D3D12·Vulkan 세 백엔드의 공유 텍스처. 1 단계에서 D3D12 부터 잰다.
- 캔버스 뷰는 지금처럼 에디터가 자기 캔버스(미러)를 그린다.

### 3.5 디버그 실행

- 메뉴에 그냥 실행과 따로 `디버그 시작` 을 둔다. 둘 다 시뮬레이션 프로세스로 돈다. 디버그 시작은 프로세스를 띄운 뒤 어댑터가 붙을 때까지 첫 프레임을 기다린다.
- 어댑터(D-319)의 대상이 에디터에서 시뮬레이션 프로세스로 바뀐다. `processName` 기본값과 [debug-adapter.md](./debug-adapter.md) 를 같이 고친다.
- 미정: 에디터가 JBro Script Editor 에 "이 프로세스에 붙어라" 를 어떻게 알릴지(제어 포트 D-270 또는 확장의 `launch`).

## 4. 단계

새 길은 다 설 때까지 설정으로만 켠다. main 의 기본은 지금 길이고, 모든 단계가 서면 기본을 바꾸고 옛 길을 지운다.

1. **실측.** 리플렉션 바이너리 스냅숏의 프레임당 비용(오브젝트 100·1000·10000), 시뮬레이션 프로세스의 시작 시간과 메모리, `InstanceId` 를 지키는지, D3D12 공유 텍스처.
2. **뼈대와 별도 창.** 실행하면 시뮬레이션 프로세스가 캔버스 글자를 받아 자기 창에서 돌고, 정지하면 끝난다. 이 단계에서 에디터 캔버스는 실행 중에 멈춰 있다.
3. **미러.** 시뮬레이션 → 에디터 프레임 상태. 실행 중 하이어라키·인스펙터·캔버스 뷰가 도는 상태를 보인다.
4. **편집과 제어.** 인스펙터 커맨드·오브젝트 만들기와 지우기·일시정지·한 프레임·스크립트 다시 싣기를 명령으로.
5. **ImGui 시뮬레이션 뷰.** 공유 텍스처와 입력 넘기기, 표시 방식 설정.
6. **디버그 시작.** 메뉴, 첫 프레임 대기, 어댑터 대상 변경, 중단점에서 에디터가 도는지 확인.
7. **옛 길 지우기.** 에디터 안의 시뮬레이션 경로(`SetSimulationEnabled`·시뮬레이션 뷰 렌더 타깃)를 지운다.

## 5. 열린 것

- 미러 비용이 크면 dirty 표시(바뀐 컴포넌트만)를 넣는다. 1 단계 실측 뒤 정한다.
- 시뮬레이션 프로세스가 서 있는 동안 고친 값은 큐에 두었다가 다시 돌 때 넣는다. 큐 상한은 미정.
- 오디오 장치를 에디터와 시뮬레이션 프로세스가 같이 여는 것(에디터의 사운드 미리 듣기와 겹칠 때)은 재지 않았다.
- 게임 화면 디버그 선(D-243), 화면 공간 UI 의 기준 해상도(D-237)가 별도 창 크기를 어떻게 따를지 미정.
